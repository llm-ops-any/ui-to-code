# 团队配置模板

> 用法：**整份复制**到项目内 `开发文档/00规则/团队配置.md`，
> 填好再开工。agent 每次进入门禁前读它。
> 本文件由人维护，**不要让 agent 自行改写角色分工**。
>
> ⚠ **复制 ≠ 重写。** 复制完只做三件事：填空、把默认档改成用户选的、删掉「（默认）」标记。
> 模板里的表格、`←` 后面的可选清单、四条刹车、门禁表都是**内容，不是占位文字**；
> 合并章节 / 缩写 / 只写当前档 = 初始化没完成（自检项见 `references/初始化自检清单.md`）。

## 角色

| 角色 | 姓名 | git email | **人编号** | 说明 |
|---|---|---|---|---|
| `PO` | | | | 定范围、验收 |
| `DEV` | | | | 设计实现、写代码 |
| `REV` | | | | 交叉评审设计与代码 |

> **一个人有多个 git email**（工作邮箱 + 个人邮箱 + 另一台机器）：**加多行，人编号填同一个**。
> 取号靠 email 查表，一个 email 查不到就会问你 —— 别让它猜。
>
> **两个人共用同一个 git 账号**（外包 / 临时同事）：这是唯一会让「人编号」失效的情况，
> 因为查表只能查到同一个 email。处理方式二选一：
> ① 给各自配独立 email（推荐）；② 启动前设环境变量 `AIDLC_PERSON=2`，技能优先读它。
> 共用账号还不设变量 ⇒ 两人会拿到同一个人编号，**审计记录将无法区分是谁做的**。
>
> **人编号**是 CR 号的第一位（`P`），1~9，**一人一个、分配后永不改**。
> CR 号 = `P` + 年末位 + 月日 + 当日序号，例 `16102100` = 人1 / 2026 / 10-21 / 当天第 00 个。
> 首位是人 ⇒ **两个人永远不共享号段**，从结构上不可能撞号。换人编号会让历史 CR 对不上人。
> 单人项目只需给自己一个 `1`。

> 2 人团队允许一人兼两角，但 `DEV` 不能给自己批代码（见 role-gates「四眼原则」）。

## 当前身份怎么判定

1. 读 `git config user.email`，在上面表格里匹配 → 得到当前角色；
2. 匹配不到 → 问用户一次「你这次以哪个角色操作？」，答案记在 `开发文档/状态.md` 的 `## Identity` 段，**同一会话内不再重复问**；
3. 切角色要显式说「我现在以 PO 身份」，agent 记录切换后继续。

## 测试策略（三选一）

**默认 `仅静态`**：开发完 → 语法/静态检查 + 人工自测主流程 → 即视为完成，不写也不跑自动化用例。

| 档位 | 做什么 | 什么时候必须升档 |
|---|---|---|
| `全量` | 新增用例 + 全量回归 + 人工走查 | 有持久化数据、有数据迁移、会多轮迭代 |
| `仅回归` | 只跑既有用例，不新增 | 改动碰了数据模型或渲染结构，但已有用例覆盖 |
| `仅静态` | 语法检查 + 静态扫描 + 人工自测 | — |

> **`仅静态` 就是绝对不跑**：不因改动类型（含持久化数据、数据迁移、换存储）破例，也不提示升档、不再询问。
> 降档必须在 `验收报告.md` 写明「未做自动化测试」及因此未覆盖的风险；静态检查不得宣称「测试通过」。
> 若某轮实际写了新用例，档位应改标 `全量`——**标签必须与实际动作一致**。

## 审批模式（五选一）

> 这张表是**五档的完整含义**，与上方「审批模式」那一行配套使用，**两处都不许删**。
> 只写当前档、把其余四档删掉，等于让后来的人以为没有别的选择。

| 模式 | 行为 | 适用 |
|---|---|---|
| `全自动` | **不设门禁**，澄清问题自答，按推荐项跑完整流程，收尾交 `验收报告.md`；只在四种情况下刹车 | 小工具、原型、试验性代码 |
| `仅需求审批` | **只留 G1**：需求可问一轮（≤5 题），`需求.md` 出来后停下等批准；批准后 G2/G3 不生效，按全自动规则跑完 | **默认**；需求要人把关、实现可托付 |
| `关键三关` | 只在 G1 需求 / G2 设计 / G3 代码合入三处停 | 2–3 人团队，要卡设计 |
| `每阶段` | 每个阶段结束都停 | 对外交付、高风险 |
| `只在交付验收` | 中间不停，最后验收一次 | 极小改动 |

**全自动模式的四条刹车**：需求自相矛盾 / 要执行不可逆或对外动作 / 与需求文档明确冲突 / 必须加需求外功能。
遇到只问一个问题，答完继续自动跑。

**全自动不等于免审计**：每次自动决策照样写进 `审计.md`（`Decision` + `Basis` + `Auto`），
跑完必须产 `开发文档/<类型目录>/CR-0X-<简称>/验收报告.md`，把「我替你决定的」逐条列出来。报告不写，视为流程未完成。

## 门禁与流转方式

| 门 | 批准人 | 文档怎么交给对方 | 对方怎么回 |
|---|---|---|---|
| G1 需求定稿 | `PO` | | |
| G2 设计定稿 | `PO` + `REV` | | |
| G3 代码合入 | `REV` | | |

> **这张表要按当前档位改，不能照抄模板**：
> `仅需求审批` ⇒ 把 G2 / G3 行标成「**本模式不生效**（自动通过，仅报备）」；
> `全自动` ⇒ 整表换成一句「无门禁，收尾交 `验收报告.md`」；
> `只在交付验收` ⇒ 只留最终验收一行。
> **留着不生效的门却不注明，等于告诉后来的人这里有三次批准 —— 实际一次都不会停。**

> 例：G1 由 `DEV` 生成 `开发文档/<类型目录>/CR-0X-<简称>/需求.md`，把仓库提交推到分支，企微发给 `PO`；
> `PO` 看完在 commit / 企微回复「批准」或「请求修改」，`DEV` 把原话贴进 `audit.md` 后继续。
