# 角色门禁（Role Gates）

**启用后本规则是硬约束。** 它决定「哪些阶段必须停」，`approve-continue` 决定「停下后怎么继续」，
两者叠加：本扩展先筛出待批阶段，`approve-continue` 再管批准与继续的分离。

> **五种审批模式**（在 `开发文档/团队配置.md` 里选一档）：
> `全自动`（不停）｜`仅需求审批`（默认，只留 G1）｜`关键三关`｜`每阶段`｜`只在交付验收`。
> 选「全自动」→ G1/G2/G3 全不生效；选「仅需求审批」→ 只保留 G1，其余按全自动跑。
> 两种都按文末对应章节执行。

## 角色模型（2–3 人小团队）

| 角色 | 代号 | 职责 |
|---|---|---|
| 产品负责人 | `PO` | 提需求、定范围、验收成果 |
| 开发 | `DEV` | 设计实现、写代码、跑测试 |
| 评审者 | `REV` | 交叉评审设计与代码，替团队把关 |

2 人团队常见映射：`PO + DEV(兼 REV)` 或 `DEV + REV(兼 PO)`。
具体谁是谁写在项目内 `aidlc-docs/team-profile.md`（模板见 `references/team-profile.template.md`）。

## 三个硬门

| 门 | 卡在哪个阶段之后 | 必须有谁批准 | 需要谁知会 | 放行条件 |
|---|---|---|---|---|
| **G1 需求定稿** | 需求分析（含用户故事，若执行） | `PO` | `DEV` | `PO` 明确说「批准」；范围与验收标准无异议 |
| **G2 设计定稿** | 工作流规划 + 应用设计 + 单元拆分 | `PO` + `REV` | `DEV` | 两人都批准：`PO` 确认范围，`REV` 确认技术可行性 |
| **G3 代码合入** | 该单元代码生成 + 构建与测试 | `REV` | `PO` | `REV` 批准 **且** 测试全部通过；`PO` 验收可选 |

`G3` 是**逐单元**的，不是整项目一次。

## 单人 / 缺角场景（重要）

`PO`、`DEV`、`REV` 由同一人担任时，**不要照搬三角色的双批规则**，否则每道门都会变成
「自己批给自己」的两次确认，纯属自找麻烦。按下面降级：

| 门 | 单人时的放行条件 |
|---|---|
| G1 | 同一人一次批准即可 |
| G2 | 同一人一次批准即可（不再要求 PO + REV 双批） |
| G3 | 同一人一次批准；audit 标 `Four-Eyes: 未满足` |

**批量批准**：`G3` 若涉及多个同类单元，允许一次批准覆盖从当前单元起的所有同类单元
（`**Batch**: unit-a, unit-b, unit-c`）。不同类、或风险明显更高的单元仍逐个批。

**不放开的一条**：`DEV` 不能给自己批代码。缺人时只能「标未四眼」，不能装作四眼齐全。

同时建议**关掉 `approve-continue`**（见 SKILL.md「预设组合」）：单人场景下批准与继续合并为一步。

## 软门（其余阶段）

除上面三处，其他阶段**不停**，也不在对话里刷屏，只需：

1. 在 `audit.md` 追加一行：`阶段：<名> ｜ 产物：<路径> ｜ 自动通过`；
2. 用户随时可以说「停」，退回该阶段重做；
3. **只在出问题时才打断**：软门阶段若发现会推翻已批准的 G1 / G2 内容，**立刻升级为硬门**，
   停下来问用户，不许自行「先改了后面再说」。

## 四眼原则

批准人不能同时是该阶段的执行人。

- 人数够：`PO` 批需求、`REV` 批设计与代码，天然四眼。
- 人数不够（2 人团队里 `REV` 兼 `PO`）：允许同一人批准，但 audit 必须标
  `**Four-Eyes**: 未满足（同一人批准）`，让历史能看出来。
- **禁止**：`DEV` 自己批准自己写的代码。这条没有例外。

## 已批准内容的变更

G1 / G2 通过后，如果需求或设计要改：

1. 停下来，向用户说明「这会影响已批准的 G1/G2」；
2. 用户确认改 → 回到对应阶段 → 重新走那道门；
3. 不要偷偷改，也不要用后面的阶段「顺手对齐」。

## 状态记录

在 `aidlc-docs/aidlc-state.md` 增加 Gates 段：

```markdown
## Gates
| Gate | Status | Approved by | At |
|---|---|---|---|
| G1 需求定稿 | approved | 张三(PO) | 2026-10-18T10:12+08:00 |
| G2 设计定稿 | pending PO | 李四(REV) 已批 | 2026-10-18T14:30+08:00 |
| G3 代码合入 / unit-timesheet-api | not-started | - | - |
```

`Status` 取值：`not-started` / `pending <角色>` / `approved` / `rejected`。
**只要有一道门不是 `approved`，后面的阶段就不能执行**（G2 未批不许进构建，G3 未批不许交付）。

## 全自动模式（不设门禁，跑完整流程）

在 `团队配置.md` 写 `审批模式：全自动` 时启用。**G1 / G2 / G3 全部不生效**，阶段之间连续执行。

### 适用范围

- ✅ 小工具、脚手架、原型、试验性代码、一次性的数据脚本
- ❌ 生产环境变更、对外交付物、涉及资金/权限/客户数据的改动
- 不做要求时**不要默认开**；用户明确写进团队配置才开

### 运行规则

1. **不停门禁**：阶段结束后直接进入下一阶段，不呈现 A/B/C，不等待确认。
2. **决策点自答**：每个需要选择的地方取「规则或文档里写明的推荐项」；没有推荐项时取**最小可行方案**，
   不得顺手加需求外的功能。
3. **澄清问题自答**：需求分析阶段的提问不抛给用户，按最合理假设作答，并把每个假设写进审计。
   深度默认 `standard`；需求已很明确时用 `minimal`。
4. **条件阶段自行判定**：按 SKILL.md 的阶段条件表判断执行或跳过，跳过必须写理由。
5. **风险标注**：任何「我自己拍的板」都要在最终报告里单列，不能埋进正文。

### 记录格式

`状态.md` 的 Gates 段统一写：

```markdown
| G1 需求定稿 | auto-approved | AIDLC 自动（全自动模式） | 2026-10-18T10:12+08:00 |
```

每次自动决策在 `审计.md` 追加一条：

```markdown
**Decision**: 单元拆分为 3 个（列表/存储/交互）
**Basis**: 需求.md 第 4 节推荐方案；无冲突信息
**Auto**: 全自动模式，未人工确认
```

### 唯一的刹车（四条，遇到必须停）

1. **需求自相矛盾**，或关键信息缺失到无法做出合理假设；
2. **不可逆 / 对外动作**：删除文件、部署、发布、发消息、付费、改动生产数据；
3. **实现与需求文档明确冲突**，且两种解释都说得通；
4. **必须新增需求外的功能**才能继续。

遇到刹车时：**只问一个问题**，拿到答案后继续全自动跑，不要借机恢复逐阶段确认。

### 收尾：一次性验收报告

流程跑完后，输出一份报告（同时写入 `开发文档/<类型目录>/CR-0X-<简称>/验收报告.md`）：

```markdown
# 验收报告
## 做了什么      ← 各阶段产出一句话 + 路径
## 跳过了什么    ← 阶段 + 理由
## 我替你决定的  ← 假设清单（重点，逐条列出，便于推翻）
## 已知风险      ← 测试未覆盖、性能未验证、兼容性等
## 建议下一步    ← 需要人工确认的 1–3 件事
```

**这份报告是全自动模式唯一的交付凭据**——门禁省掉的确认，全部由它补回来。报告不写，等于没有。

## 仅需求审批模式（只留 G1）

在 `团队配置.md` 写 `审批模式：仅需求审批` 时启用。**G2 / G3 不生效，只保留 G1**。

适用：中等规模、需求最容易跑偏但实现部分可以信任 AI 的项目。**需求是唯一值得人把关的地方**，
设计和代码交给流程自己走。

### 流程

1. **需求阶段（半自动）**：允许澄清提问，但建议**一次问完、不超过 5 题**，只问真正影响范围的问题。
   用户不答、或说「你定」→ 按推荐项自答，假设逐条写进审计。
2. 产出 `开发文档/<类型目录>/CR-0X-<简称>/需求.md` → **G1 停下**，给门禁选项（无 `approve-continue` 时三步并一步）。
   G1 未批准，**不许进入工作流规划及之后任何阶段**。
3. G1 批准 → **之后全自动**：完全按上一章「全自动模式」的规则连续执行，
   G2 / G3 不再出现，决策取推荐项，澄清问题自答，四条刹车照旧。
4. 收尾仍然要交 `开发文档/<类型目录>/CR-0X-<简称>/验收报告.md`。

### 与全自动模式的唯一差别

| 点 | 全自动 | 仅需求审批 |
|---|---|---|
| G1 | 不停 | **必须人工批准** |
| 需求澄清 | 全部自答 | 可问一轮（≤5 题），再自答 |
| G2 / G3 | 不停 | 不生效 |
| 刹车 3（冲突） | 与需求文档冲突即停 | 与**已批准**的 `需求.md` 冲突即停，**不许自行改需求迁就实现** |

### 记录

`状态.md` 的 Gates 段：

```markdown
| G1 需求定稿 | approved | 张勇 | 2026-10-18T16:05+08:00 |
| G2 设计定稿 | skipped | 仅需求审批模式 | - |
| G3 代码合入 / 待办清单 | skipped | 仅需求审批模式 | - |
```

G1 前后按正常审计格式记（含原始输入）；G1 之后的每条决策按全自动格式记
`Decision / Basis / Auto`，并在 `Auto` 里注明「仅需求审批模式，G1 后自动执行」。
