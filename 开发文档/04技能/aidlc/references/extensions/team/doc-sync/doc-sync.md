# 文档同步

**启用后本规则是硬约束。**

## 为什么

AIDLC（和所有 SDD 框架）最常见的腐烂方式：代码在编码阶段被反复调整，但没人回头改需求文档和设计文档。
迭代几轮之后，`aidlc-docs/` 里的文档就彻底失去参考价值，只剩一堆代码——这恰恰是要避免的结局。

## 何时触发

| 触发点 | 动作 |
|---|---|
| 代码生成阶段结束 | 必查：实现是否偏离了已批准的设计 |
| 用户中途改需求 | 必查：需求文档、用户故事、设计是否要一起改 |
| 修 bug 改变了行为 | 必查：需求/设计里描述的预期行为是否要更正 |
| 结构性重构 | 必查：应用设计、单元拆分是否要重写 |

纯实现细节（重命名局部变量、格式化、日志措辞）不触发。

## 怎么做

1. 读 `aidlc-docs/aidlc-state.md`，列出已执行的阶段；
2. 建立「改动 → 受影响文档」映射，只挑**真的会因此过期的**，不要全量重写；
3. 更新方式：
   - 段落级替换，保留文档其余部分；
   - 在文档头部维护一行 `> 最后同步：YYYY-MM-DD HH:MM（对应改动：<一句话>）`；
4. 在 `audit.md` 追加一条：
   ```markdown
   **Doc Sync**: 更新 3 个文件（requirements.md / application-design.md / 单元-1/functional-design.md）
   **Reason**: 修 bug 时把「重复提交」从拒绝改成幂等返回，与需求文档里「拒绝重复」冲突
   ```
5. 阶段完成消息里报一行：`文档同步：更新 N 个文件`。

## 冲突时停下来

如果发现代码行为与已批准文档矛盾，**且用户没说明以哪边为准**：

1. 不要自己决定改文档还是改代码；
2. 停下来向用户指出具体矛盾（文档哪一段 vs 代码哪一处）；
3. 得到明确指示后再动手，并把这次决策记进 audit。

## 与门禁的关系

文档同步属于本阶段的一部分，**在门禁之前做完**。不要「先批准、后补文档」——
那等于批准了一份已知过期的文档。
