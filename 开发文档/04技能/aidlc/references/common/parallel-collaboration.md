# 多人并行协作规则（AIDLC 扩展）

> **适用**：同一项目多人（或多 agent 会话）同时推进不同需求。
> **触发**：项目里出现第二个人/第二个会话时，**必须**先读本文件并按此改造目录结构。

---

## 一、为什么单轨编号会撞

AIDLC 默认假设「一次一轮、串行推进」，所以轮次号 `R1, R2, …` 是**单轨序号**。
并发时两个人同时开工，都会看到「上一轮是 R6」⇒ 都取 `R7` ⇒ 撞号。

**2026-10-21 事故**：两条线都编成 R7（CR-7 / v1.7 / §2.11），合入时 19 处冲突
（代码 5 / 需求 7 / 状态 4 / 审计 3），且两侧的需求编号 FR-48~ 完全重叠，只能整段重编。

**根因不是「谁不守规矩」，是「序号被当成标识用」。**

---

## 二、三条铁律

### 铁律 1：编号唯一，开工先占号

**轮次号 `R` 只用于展示排序，唯一标识一律用 `CR-<8位号>`。**

开工第一步（写任何文档、改任何代码之前）：**建 CR 目录本身就是在取号**。

```
开发文档/<类型目录>/CR-<8位号>-<简称>/    # 例：需求/CR-16102100-导出CSV/
                                          # 类型 = 需求 / 缺陷 / 技术债（见 SKILL.md）
```

**目录名就是号**，不需要额外的「号段文件」。号的构成：

```
P Y MMDD N
│ │ │    └─ 当天第几个（00~99）
│ │ └────── 月日
│ └──────── 年（末位，2026 → 6）
└────────── 人编号（团队配置里定，一人一位，分配后不改）
```

| 谁 | 日期 | 第几个 | 号 |
|---|---|---|---|
| 张勇（人 1） | 2026-10-21 | 00 | **16102100** |
| 张勇（人 1） | 2026-10-21 | 01 | 16102101 |
| 李四（人 2） | 2026-10-21 | 00 | **26102100** |
| 张勇（人 1） | 2027-10-21 | 00 | 17102100 |

**为什么不要单独的占号文件**：号是**算出来的**，不是抢的。一份「号段文件」只为了记「这个号有人用了」，
而目录名已经说明了这件事；CR 目录里本来也有提出人、时间、原话、号段。
多一个文件 = 多一处要维护、多一次提交、多一处要同步。

**取号三步**（第一步必须是 `git pull`）：

1. **`git pull`** —— 看到**所有人、包括你自己别的电脑**已占的号。跳过这步必撞。
2. 查人编号 `P`（`团队配置.md` 或环境变量 `AIDLC_PERSON`）；`Y` = 今年末位；`MMDD` = 今天；
   `N` = `<类型目录>/CR-<P><Y><MMDD>*/`（含类型那层）已有几个（**从 00 起**：一个都没有取 00，已有一个取 01）；
   建 `<类型目录>/CR-<P><Y><MMDD><N>-<简称>/`。
3. 至少写一个 `状态.md`（阶段可写 `not-started`，表示「占了号、还没开工」）
   → `git add` + `commit` + **`push`**。**被拒是正常的**（别人先推了）：
   `pull` → 重算 `N` → 再推。这不是异常处理，是日常流程。

> **同一个人两台电脑**：人编号相同是对的（还是你），撞的是序号 —— 靠第 3 步的 push 仲裁。
> **两个人共用一个 git 账号**：人编号会重复，审计也分不清人。给各自配独立 email；
> 不行就设 `AIDLC_PERSON=2` 覆盖（技能优先读环境变量，读不到才查 email 表）。

> 2026-10-21 真撞过一次：两条线都取 CR-2，**当时占号文件按「日期-名字-短名」命名**，
> 两个不同文件名并存、撞号完全静默，直到合并才发现 CR 号、FR 段（13~16 vs 13~15）全重叠。
> 教训是：**号必须在文件路径层面可见** —— 这就是为什么 CR 目录名必须含号。

**一天最多 100 个**（序号 00~99，从 00 起）。不够用再加一位。

> 不要往 `状态.md` 里写占号记录——那是共享单文件，并发写必冲突。

### 铁律 2：一人一分支，G3 之后才合

```bash
git switch -c iter/CR-16102100-软删除
# …开发…
git switch main && git pull --rebase
git switch iter/CR-16102100-软删除 && git rebase main   # 每天至少一次，避免长期分叉
# G3 通过后
git switch main && git merge --no-ff iter/CR-16102100-软删除
```

**禁止**直接往 `main` 推。**禁止**两个人在同一分支上开发。

### 铁律 3：先合不改号，后合改号

两条线意外撞号时，**已进 main 的不动**，后合的整条线重编：

| 项 | 后合者怎么改 |
|---|---|
| `CR-7` | → `CR-8`（全文替换，含审计、状态、问题记录） |
| `v1.7` | → `v1.8` |
| `§2.11` | → 顺延到下一个空章节 |
| `FR-48~59` | → 整体平移到 `FR-57~68`（按最大号 +1 起） |
| `AC / NFR / S` | 同理按号段平移 |

> **别只改标题**。编号在正文里会被引用（`见 FR-57 ④`），漏改会造成死引用。
> 重编后用一条命令自查：`grep -o 'FR-[0-9]*' 需求.md | sort | uniq -d` 应为空。

## 三、目录改造：把「共享单文件」拆成「一人一份」

冲突量最大的不是代码，是**所有线都往同一份文档的同一处写**。按下面拆，冲突面能从 19 降到接近 0。

| 现在（易冲突） | 改成（不冲突） |
|---|---|
| `需求.md` 一个文件装所有 CR 的章节 | `需求.md` 只留**索引**（FR 总表）；每轮增量单独 `需求/增量/CR-8.md` |
| `状态.md` 的 `## Current` 单块 | `状态.md` 只放**指针表**；每轮实况 `状态/CR-8.md` |
| `审计.md` 一条长文件末尾追加 | 按人分片 `审计/<日期>-<名字>.md`；收尾时按时间合并 |
| `todolist.html` 单文件 2900 行 | 拆 `storage.js` / `store.js` / `view.js` / `controller.js` |

**共享文件只允许「追加一行」的操作，不允许「改同一行的内容」。**
`状态.md` 的指针表就是按这个原则设计的——每轮加一行，不改别人的行。

### 3.1 已落地的形态：`开发文档/00规则/文档结构.md`

把「按阶段分」改成**按需求分目录**，是上一节思路的完整版（2026-10-21 在待办清单项目实装）：

```text
开发文档/
├── 00规则/      团队配置.md  协作规范.md  文档结构.md
├── 01需求/      CR-00-初始版本/  CR-<8位号>-<简称>/（目录名就是号）
├── 02缺陷/      CR-<8位号>-<简称>/
├── 03技术债/    CR-<8位号>-<简称>/
├── 04技能/      _汇总/(生成·不入库)
```

**关键约束：一个 ID 只有一处正文。** 新 ID 写进对应 CR 的 `需求.md`；跨 CR 引用写
`CR-<8位号>/FR-n`，不复制正文。需求有变化 = 新开 CR + 新 FR，**不改既有 CR 的历史正文**——
否则同一条 FR 会出现两份互相矛盾的定义。

**布局已固定为技能默认**（2026-10-21 起不再有第二种），`文档结构.md` 只记录**项目级补充**，
不再用它切换布局 —— 先前「项目自定义布局」导致技能文档和工具各认一套，`汇总.py` 在新项目里直接失效。

> 结果对照：拆之前一次合并 19 处冲突（代码 5 / 需求 7 / 状态 4 / 审计 3）；
> 拆之后需求与目录类冲突**降为 0**，剩余只在 `todolist.html`（单文件，需另行拆模块）。

## 四、合并动作的标准流程

出现冲突时按此顺序，**不要凭感觉选边**：

```bash
git diff --name-only --diff-filter=U     # 1. 列出冲突文件
grep -c '^<<<<<<<' <文件>                # 2. 数冲突块，心里有数
```

3. **文档类**：两边都留 —— 后到者整条线重编号，然后按「章 → 号段 → 变更记录」顺序拼接
4. **代码类**：按语义合并，逐块判断「这两个改动是否互相排除」
   - 加字段 ⇒ 都保留
   - 改同一函数的不同分支 ⇒ 都保留，注意逗号/顺序
   - 改同一行逻辑 ⇒ 必须先想清语义，可能两边都对（如本次：先判回收站、再判搜索）
5. **静态检查**：`node --check`（或对应语言的语法检查）+ 关键符号引用计数
6. **记录**：`审计.md` 写一条 `[合并 / 编号冲突解决]`，写清重编映射与每块代码的合并理由

> 若项目测试策略不是 `仅静态`，合并后**必须**跑全量回归——语义合并是最容易引入静默回归的场景。

## 五、开工前自检清单

- [ ] `开发文档/<类型目录>/CR-<P><Y><MMDD><N>-<简称>/` 已建（含状态.md）、已 commit、**已 push**
- [ ] 我在自己的分支 `iter/CR-<8位号>-<短名>` 上，不在 main
- [ ] `git rebase main` 是今天做过的
- [ ] 本轮要改的文件，别人这轮是否也在改（看对方的占号文件「需求」一行）
- [ ] 若会同时改同一文件：先约定谁先合，后者负责重编号
