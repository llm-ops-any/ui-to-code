# 领域补充 · 服务端 / 后端服务

> 按需加载：做 API 服务、后台系统、数据服务时读这一页。
> **主流程不变**，这里只说服务端特有的东西。

## 一、为什么服务端要单独一页

| 差异 | 后果 |
|---|---|
| **接口是对外承诺** | 改一个字段名，可能打断别人的客户端 —— 不能像网页一样"刷新就生效" |
| **数据迁移不可逆** | 删列、改类型，回滚要单独设计；线上跑一半失败最麻烦 |
| **多环境** | dev 能跑 ≠ staging 能跑 ≠ prod 能跑 |
| **出问题没人看着** | 网页崩了用户会刷新，服务崩了要自己发现 |

## 二、额外要写的文档

### 1. `设计/接口契约.md`

一个接口一节，**写清楚到能照着写客户端**：

```markdown
### GET /api/orders

- **用途**：按条件查订单列表
- **鉴权**：Bearer token（scope: orders:read）
- **入参**
  | 参数 | 类型 | 必填 | 默认 | 约束 |
  |---|---|---|---|---|
  | status | string | 否 | all | pending/paid/cancelled |
  | page | int | 否 | 1 | ≥1 |
  | size | int | 否 | 20 | 1~100 |
- **出参**：`{ items: Order[], total: int, page: int }`
- **错误码**：401 未鉴权 / 403 无权限 / 422 参数非法
- **幂等性**：GET 天然幂等
- **限流**：60 次/分钟/用户
```

**必须写清的三个字段，最常被漏**：
- **错误码**：客户端要按码分支，不能靠猜 message
- **幂等性**：POST 重复提交会怎样？不写清，前端就得自己防重
- **分页语义**：`page` 从 1 还是 0？`total` 是总数还是本页数？

### 2. `设计/数据迁移.md`（有 schema 变更时必写）

```markdown
## 迁移：orders 加 channel 字段

- **变更**：`ALTER TABLE orders ADD COLUMN channel VARCHAR(16) NOT NULL DEFAULT 'web'`
- **向前兼容**：老代码不读这个字段，可共存
- **回滚**：`ALTER TABLE orders DROP COLUMN channel`（**确认无新代码写入后再执行**）
- **数据影响**：存量 120 万行，加默认值走 PG 11+ 的 fast default，不重写表
- **执行窗口**：低峰期，预计 < 1s
- **验证**：迁移后抽查 100 条、确认默认值正确
```

**三条铁律**：
1. **必须能回滚**，且回滚语句要写出来、验证过 —— 不能只写"回滚见代码"
2. **先兼容后删除**：加字段（兼容）→ 双写/读新 → 确认无老代码 → 再删旧字段。**别一步删**
3. **大表加索引要并发建**（PG 的 `CREATE INDEX CONCURRENTLY`、MySQL 的 `ALGORITHM=INPLACE`），否则锁表

### 3. `运维说明.md` 里的环境矩阵

| 项 | dev | staging | prod |
|---|---|---|---|
| 地址 | localhost:8080 | stg.example.com | api.example.com |
| 数据库 | 本地 docker | 独立实例 | 主从 + 只读副本 |
| 日志级别 | debug | info | warn |
| 限流 | 关 | 宽松 | 按契约 |
| 数据 | 假数据 | 脱敏抽样 | 真实 |

**环境差异要显式列表**，不要靠"看配置文件"。90% 的"本地能跑线上不行"都在这张表里。

## 三、测试怎么做

`仅静态` 对这类型项目**不够**。至少要：

| 层 | 做什么 | 何时 |
|---|---|---|
| 接口测试 | 每个端点：正常 / 参数非法 / 无权限 / 不存在 | 每次改动 |
| 迁移验证 | dev 库跑一遍 → 回滚 → 再跑一遍 | 有 schema 变更时 |
| 冒烟 | 部署后打 3~5 个核心端点 | 每次部署 |
| 压测（可选） | 关键接口的 P95 延迟 | 上线前 / 大改动后 |

`团队配置.md` 的测试策略建议选 `全量`，至少 `仅回归`。

## 四、常见坑

| 坑 | 表现 | 处置 |
|---|---|---|
| 加必填字段 | 老客户端立刻 400 | 新字段必须可空或有默认；先兼容再收紧 |
| 迁移写一半失败 | 表结构半新半旧 | 迁移拆小步、每步可独立回滚；有事务的用事务 |
| 环境配置写死 | 上线才发现指向 dev 库 | 全部走环境变量；启动时校验必填项，缺失直接退出 |
| 日志打到 stdout 混业务输出 | 采集器把业务数据当日志 | 结构化日志（JSON）到 stderr 或文件 |
| 深翻页用 offset | 第 10000 页越翻越慢 | 改游标分页（`where id > last_id limit n`） |
| N+1 查询 | 列表 100 条查了 101 次库 | 批量查 + 内存组装；或 join |
| 时区/编码不一致 | 差 8 小时、中文乱码 | 统一 UTC 存储、展示层转换；连接强制 utf8mb4 |
| 没有健康检查 | 挂了要等用户报 | 加 `/healthz`（只探活）和 `/readyz`（探依赖） |

## 五、和主流程怎么接

- **需求**：写清"谁调用、调用量级、能接受多长延迟"——这决定要不要缓存、限流
- **决策记录**：数据库选型、同步还是异步、单体还是拆服务、鉴权方案，都该留痕
- **运维说明**：环境矩阵 + 部署步骤 + 回滚步骤
- **验收报告**：AC 里带上接口测试结果和迁移验证结果
