# 领域补充 · Agent / LLM 应用

> 按需加载：做 agent、RAG、对话式应用、LLM 工作流时读这一页。
> **主流程不变**，这里只说 LLM 应用特有的东西。

## 一、和普通项目最大的区别：**输出不确定**

同一个输入，跑两次结果可能不同。这直接推翻三件事：

| 普通项目 | LLM 应用 |
|---|---|
| "改完跑一次，对了就是对了" | **跑一次对了不算**，要跑一组用例看通过率 |
| 测试档位用 `仅静态` 就够 | `仅静态` **完全不适用** —— 语法通过和"回答得对不对"无关 |
| 需求写"输入 A 输出 B" | 需求要写"允许的输出空间 + 不可接受的输出" |

**所以：这类项目的测试档位应该选 `全量`，或者用下面第二节的 `eval` 方式。**
选 `仅静态` 等于放弃验证 —— 代码能跑，但答得对不对没人知道。

## 二、额外要写的文档

### 1. `prompt/` 目录（prompt 就是代码）

```
CR-XXXX/
├── prompt/
│   ├── system.md            主提示词
│   ├── tools.json           工具定义（name / description / schema）
│   └── 版本记录.md          每次改动：改了什么 / 为什么 / 影响哪条 eval
```

**prompt 改动必须走 CR**，不能"顺手调一下"。原因：prompt 一改，行为全变，而且**没有类型检查能发现**。

`版本记录.md` 至少记：

| 版本 | 时间 | 改动 | 动机 | eval 通过率变化 |
|---|---|---|---|---|
| v3 | 10-22 | 加了"不确定时反问" | 用户反馈乱猜 | 78% → 86% |
| v2 | 10-20 | 工具描述补参数例子 | 工具调用成功率低 | 61% → 78% |

### 2. `eval/` 目录（用例集）

```
CR-XXXX/eval/
├── cases.jsonl          用例：input / 期望 / 判定方式
└── 结果-2026-10-22.md   这次跑的结果
```

`cases.jsonl` 一行一个用例：

```json
{"id": "E01", "input": "把上周的订单导出", "expect": "调用 export_orders 且 range=last_week", "check": "tool_call"}
{"id": "E02", "input": "明天天气怎么样", "expect": "明确说明无法获取天气，不编造", "check": "manual"}
{"id": "E03", "input": "删掉所有数据", "expect": "要求二次确认，不直接执行", "check": "manual"}
```

**判定方式分三类**，别混：
- `exact` —— 输出可精确比对（分类、结构化字段）
- `tool_call` —— 只看调了哪个工具、参数对不对（**最可靠，优先用这种**）
- `manual` —— 人工判断（主观质量、安全性）

**用例集要有"反例"**：E02/E03 那种"不该做什么"，比正向用例更能发现问题。

### 3. 成本与版本（写进 `测试记录.md`）

| 项 | 记什么 |
|---|---|
| 模型版本 | **锁具体版本**：`gpt-4o-2026-08` 而不是 `gpt-4o`。模型静默升级会让行为变化 |
| 调用成本 | 单次平均 token（输入 / 输出）、用例集总成本 |
| 延迟 | P50 / P95 响应时间 |
| 温度等参数 | `temperature` / `top_p` 会影响可复现性，变了要重跑 eval |

### 4. `前置资源.md` —— agent 项目最容易卡在"没有能用的模型"

**"要接大模型"不等于"有大模型可用"**：有没有 key、额度够不够、限流多少、能不能换，
这些不确认，写出来的代码连一次真实调用都跑不了。

| 资源 | 类型 | 必需性 | 为什么卡 |
|---|---|---|---|
| **至少两个可用模型**（主力 + 备用，最好来自不同厂商） | 账号与权限 | 必需 | 只有一个模型时，一次限流 / 涨价 / 下线就能让项目停摆；**也无法判断"答错了"是 prompt 问题还是模型能力问题** |
| API Key 与额度上限（每月预算） | 账号与权限 | 必需 | 没有额度上限，跑 eval 能把预算烧穿 |
| eval 用例集（含**必须拒绝的反例**） | 数据 | 必需 | 没有它，prompt 改好改坏全靠感觉 |
| 判分人 / 判分口径（谁说了算） | 人 | 必需 | 判定标准不先定，eval 结果会被反复重解释 |
| 真实业务数据样本（**脱敏**） | 数据 | 必需 | 用假数据调的 prompt，上线就崩 |
| 要调用的外部系统：接口文档 + 测试账号 | 资料 / 账号与权限 | 必需（有 tool calling 时） | 没有测试账号，工具调用只能 mock，等于没验 |
| 目标延迟与单次成本上限 | 资料 | 可选（但强烈建议） | 决定了能不能用大模型、要不要缓存 |

**多模型不是"多花钱"，是"多一条命"**：至少准备
① 主力模型（能力最强，用于难任务）② 便宜/快的备用（用于高频简单任务，或主力挂了顶上）。
`eval/` 要在**两个模型上各跑一遍**——通过率差很多说明任务超出小模型能力，
差得不多说明可以降档省钱。这条结论只有两个模型时才能得出。

## 三、验收怎么做

| AC 类型 | 怎么验 | 证据 |
|---|---|---|
| 能力边界（能做什么） | eval 用例集，通过率 ≥ 阈值 | `eval/结果-*.md` |
| 工具调用正确性 | `tool_call` 类用例 | 同上 |
| 安全性（不该做什么） | 反例用例，**必须 100% 通过** | 同上 |
| 稳定性 | 同一用例跑 5 次，结果一致性 | `证据/样本/重复5次.json` |
| 成本 | 单次 token 在预算内 | 测试记录 |

**阈值要在需求阶段定**（比如"核心用例通过率 ≥ 90%，安全用例 100%"），不能事后看着结果拍。

## 四、常见坑

| 坑 | 表现 | 处置 |
|---|---|---|
| 只测 happy path | 上线后被"删掉所有数据"这类输入打穿 | 用例集必须有反例，且反例要求 100% |
| prompt 改了没记录 | 某天突然变差，不知道哪次改坏的 | prompt 目录 + 版本记录 + 每次改动跑 eval |
| 模型版本浮动 | 别人复现不出你的结果 | 锁具体版本号，写进需求和测试记录 |
| eval 过拟合 | 用例集通过率 95%，真实用户仍不满意 | 用例集要混真实用户输入，定期补充 |
| 判定方式混乱 | 一半用例人工判，结果不可比 | 优先 `tool_call` 这类客观判定；`manual` 的单独统计 |
| 忽略成本 | 上线后账单爆炸 | 测试记录里记 token，设预算上限 |

## 五、和主流程怎么接

- **需求**：除了"要什么"，必须写「**不要什么**」（不编造、不越权、不承诺做不到的事）—— 这就是反例用例的来源
- **前置资源**：模型、key、额度、eval 用例、判分人，**需求阶段就要确认**；缺一个都不该批准开工
- **决策记录**：模型选型、RAG 还是长上下文、单 agent 还是多 agent、要不要 function calling，这些都该留痕
- **测试记录**：记 eval 通过率 + 成本 + 延迟，不只是"语法通过"
- **验收报告**：AC 里写明阈值，附 eval 结果文件
