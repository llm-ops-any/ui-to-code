# 领域补充 · CLI / 工具类项目

> 按需加载：做命令行工具、脚本、批处理工具时读这一页。
> **主流程不变**，这里只说 CLI 特有的东西。

## 一、为什么 CLI 要单独一页

CLI 的用户不是"看界面的人"，是**脚本和管道**。所以：

| 差异 | 后果 |
|---|---|
| **输出被程序消费** | 人看得懂不够，要能被 `grep` / `jq` / 循环处理 |
| **退出码承载语义** | 脚本靠 `$?` 分支，永远是 0 = 无法判断成败 |
| **会被重复执行** | 幂等性不是加分项，是必需 |
| **没法"刷新页面"** | 出错信息必须一次说清 what / why / how to fix |

## 二、额外要写的文档

### 1. `设计/命令契约.md`

一个命令一节：

```markdown
### mytool export

- **用途**：导出数据到 CSV
- **用法**：`mytool export --from <date> [--to <date>] [--out <path>]`
- **参数**
  | 参数 | 必填 | 默认 | 说明 |
  |---|---|---|---|
  | --from | 是 | — | 起始日期 YYYY-MM-DD |
  | --to | 否 | 今天 | 结束日期（含） |
  | --out | 否 | stdout | 输出文件；`-` 表示 stdout |
  | --json | 否 | false | 以 JSON 输出（供脚本消费） |
- **退出码**：0 成功 / 1 一般错误 / 2 参数错误 / 3 数据源不可达
- **幂等**：重复执行结果相同（覆盖写）；`--append` 除外
- **副作用**：写 `--out` 指定的文件；不修改数据源
```

**必须写清三样**：
- **退出码**：每个码对应什么情况，脚本要能判断
- **幂等性**：重复跑会怎样？追加还是覆盖？
- **副作用**：会不会改数据源？会不会发网络请求？

### 2. 破坏性命令的说明（`设计/命令契约.md` 里单列一节）

删除、覆盖、迁移这类命令，必须写：

```markdown
### mytool purge  ⚠ 破坏性

- 作用：永久删除 N 天前的记录
- **保护**：必须同时给 `--yes` 和 `--older-than`，否则拒绝执行
- **预演**：`--dry-run` 只打印将删除的数量，不动数据
- **不可恢复**：删除前请先备份
```

**破坏性命令的标准配置**：`--dry-run` + 二次确认（`--yes`）+ 明确说明不可恢复。

## 三、四条硬约定

### 1. 退出码

| 码 | 含义 |
|---|---|
| 0 | 成功（含"没有要做的事"） |
| 1 | 一般错误（业务失败、找不到数据） |
| 2 | 用法错误（参数缺失/非法） |
| 3+ | 按需细分（网络、权限、依赖缺失） |

**最忌**：出错也 `exit 0`，只在日志里写"失败"。脚本没法判断。

### 2. stdout / stderr 分离

- **stdout**：只放**结果数据**（能被管道消费）
- **stderr**：日志、进度、警告、错误

否则 `mytool export > data.csv` 会得到一堆日志混在 CSV 里。

### 3. 非 TTY 时不刷进度条

```python
if sys.stdout.isatty():
    show_progress_bar()
```

重定向到文件时进度条会变成几万行 `\r` 垃圾。

### 4. 配置优先级

```
命令行参数  >  环境变量  >  配置文件  >  内置默认
```

写进契约里，不要让人猜。常见做法：`--config` 指定文件，`MYTOOL_*` 环境变量。

## 四、验收怎么做

CLI 的验收**就是命令行为**，可以直接写进 AC：

| AC 类型 | 怎么验 |
|---|---|
| 正常路径 | 跑一遍，比对 stdout 内容 |
| 参数错误 | 缺参数 → 退出码 2 + stderr 有用法提示 |
| 空结果 | 没有数据 → 退出码 0 + 明确说"无匹配"（不是静默） |
| 幂等 | 连跑两次，第二次结果相同或明确跳过 |
| 管道 | `mytool ls --json \| jq '.[0]'` 能正常消费 |
| 破坏性 | 无 `--yes` 时拒绝执行；`--dry-run` 不动数据 |

`证据/` 里放命令输出（`证据/样本/ac-01.out`）比截图更合适。

## 五、常见坑

| 坑 | 表现 | 处置 |
|---|---|---|
| 日志混进 stdout | 管道拿到的数据被污染 | 日志一律 stderr |
| 退出码永远是 0 | 脚本判断不了成败 | 按上面的码表返回 |
| 破坏性操作没预演 | 手滑删库 | 必须 `--dry-run` + `--yes` |
| 报错只说"失败" | 用户不知道怎么修 | 三段式：发生了什么 / 为什么 / 怎么解决 |
| 不支持管道 | 无法组合 | 支持 `-` 作文件名表示 stdin/stdout；提供 `--json` |
| 相对路径踩坑 | 换个目录跑就找不到文件 | 路径一律基于 cwd 解析；配置文件用绝对路径 |
| 交互式提示无法自动化 | CI 卡住 | 需要交互的地方提供 `--yes` / `--non-interactive` |
| 版本升级破坏脚本 | 用户脚本突然报错 | 输出格式变更算 breaking change；加 `--version` 便于排查 |

## 六、和主流程怎么接

- **需求**：核心是"命令怎么用"和"输出长什么样"——把命令示例直接写进需求
- **决策记录**：用哪种参数解析库、配置格式（yaml/toml/env）、是否提供交互模式，值得记
- **测试档位**：`仅静态` 常常够（工具类项目轻），但**退出码和 stdout 必须人工验一遍**
- **验收报告**：AC 直接写"跑 `mytool xxx`，退出码应为 N，stdout 应包含 …"
