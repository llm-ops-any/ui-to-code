# 领域补充 · 三维可视化项目

> 按需加载：做三维 / WebGL / 数字孪生 / 可视化大屏类项目时读这一页。
> **主流程不变**（还是 需求 / 状态 / 设计 / 验收 / 决策），这里只说三维特有的东西。

## 一、为什么三维要单独一页

三件事让它和普通 web 项目不一样：

| 差异 | 后果 |
|---|---|
| **资产体积大** | 模型、贴图动辄几十上百 MB，塞进 git 会撑爆仓库 |
| **性能有硬指标** | 帧率、面数、显存是**验收项**，不是"优化项" |
| **视觉验收偏主观** | "看着不对"说不清，必须有前后截图对照 |

## 二、额外要写的文档

在 `CR-XXXX/` 里加两份（不必等设计阶段，需求阶段就该有）：

### 1. `资产清单.md`

| 资产 | 类型 | 体积 | 来源 | 许可 | 进 LFS |
|---|---|---|---|---|---|
| `scene/city.glb` | 模型 | 42 MB | 美术提供 2026-10-20 | 自有 | ✓ |
| `tex/road_diffuse.jpg` | 贴图 | 3.1 MB | Poly Haven | CC0 | ✗ |

- **来源和许可必须记**：客户交付 / 商用项目里，一个 CC-BY 资产没署名就是法律问题。
- **`>5 MB` 走 git LFS**，别直接提交。`.gitattributes` 加：
  ```gitattributes
  *.glb *.gltf *.fbx *.obj binary
  *.jpg *.png filter=lfs diff=lfs merge=lfs -text
  ```
  已经在仓库里的大文件，用 `git lfs migrate import --include="*.glb"` 迁。

### 2. `性能预算.md`（或写进 `设计/` 一节）

**先定预算，再动手**。没有预算的三维项目，最后一定在"加个特效"和"掉帧"之间反复拉扯。

| 项 | 预算 | 实测 | 设备基线 |
|---|---|---|---|
| 三角面数 | ≤ 200k | — | iPhone 12 / GTX 1650 |
| Draw calls | ≤ 150 | — | 同上 |
| 贴图总显存 | ≤ 256 MB | — | 同上 |
| 首屏可交互 | ≤ 3 s | — | 4G 网络 |
| 稳定帧率 | ≥ 50 fps | — | 同上 |

**设备基线必须写**：不写清"在什么机器上跑 50 帧"，这个数字没有意义。

### 3. `前置资源.md` —— 三维项目最常缺的从来不是代码

**三维项目的"做不了"几乎都是资产没到**：模型没有、设计图只有一张效果图、目标机不知道是啥。
这些必须在 G1 前摆出来（格式见 `common/risk-and-resources.md`）。

| 资源 | 类型 | 必需性 | 为什么卡 |
|---|---|---|---|
| 模型源文件（glb/gltf/fbx，**带层级和正确命名**） | 素材 | 必需 | 只有一个合并的整体模型 ⇒ 做不了点击选中 / 单独动某个部件 |
| 场景设计图（平面 + 立面 + 关键视角） | 资料 | 必需 | 只有效果图 ⇒ 相机走位、遮挡关系、尺度全靠猜，做完必返工 |
| 贴图 / HDRI（含来源与许可） | 素材 | 可选 | 缺了能用纯色先跑，但交付时一定要补 |
| 品牌 logo / 字体 / VI 手册 | 资料 | 可选 | 缺了用系统字体，交付前替换 |
| **目标设备**（型号 / 显卡 / 是否手机端） | 环境 | 必需 | 决定面数与贴图预算；不知道就是蒙着做 |
| 参考效果（竞品链接 / 视频） | 资料 | 可选 | 有它能省一轮"这不是我要的感觉" |
| 资产商用许可（模型、贴图、字体） | 人 | 必需（商用项目） | 客户交付里出现来源不明资产 = 法律风险 |
| 部署环境的网络限制（CDN / 内网） | 环境 | 必需（内网项目） | 模型加载不出来，页面一片空白且**不报错** |

**降级方案怎么写**：缺模型时的标准做法是「**先用占位盒体把交互和相机走通**」，
但要在 `需求.md` 写明：**占位阶段不算交付**，验收必须用真实资产。否则容易"占位跑通了就当完事"。

## 三、验收怎么做

三维的验收证据**不能只有文字**：

| 证据 | 放哪 | 说明 |
|---|---|---|
| 首屏截图 | `证据/截图/首屏.png` | 与需求描述对照 |
| 关键交互截图 | `证据/截图/交互-01.png` … | 每个 AC 一张 |
| 录屏（动效 / 相机运动） | `证据/录屏/ac-02.mp4` | 静态图看不出流畅度 |
| 性能面板截图 | `证据/截图/性能.png` | 帧率 / draw calls / 显存，对应预算表 |
| 帧率采样（可选） | `证据/样本/fps.csv` | 用 `performance.now()` 打点导出 |

`验收报告.md` 里逐条 AC 引用这些文件，**不要只说"看起来正常"**。

## 四、常见坑（踩过的记在这里）

| 坑 | 表现 | 处置 |
|---|---|---|
| 模型单位不一致 | 导入后大小差 100 倍 | 资产清单里记单位（米 / 厘米），导入时统一缩放 |
| 坐标系不同 | Y-up 和 Z-up 混用，模型躺着 | 在 `设计/` 里写明用哪套，转换只在导入层做 |
| 光照烘焙丢失 | 换渲染器后阴影全没了 | 烘焙结果和模型一起进资产清单 |
| 贴图没压缩 | 显存爆掉、移动端直接崩 | 上线前统一转 KTX2 / Basis |
| 资产直接提交 | 仓库从几十 MB 涨到几 GB | **一开始就配 LFS**，事后迁移很痛 |

## 五、和主流程怎么接

- **需求**：三维需求常带"参考效果"（截图 / 竞品链接），贴进 `需求.md` 的原文区
- **前置资源**：模型、设计图、目标设备，**需求阶段就要问**，别等设计完才发现没有
- **决策记录**：渲染方案（Three.js / Babylon / Cesium / 自研）、模型格式（glTF / 3DTiles）、压缩方案，这些都该留 `决策记录.md`
- **测试档位**：仍可用 `仅静态`（三维的"测试"主要是人工看 + 性能采样），但要跑一次 `性能预算.md` 的实测
