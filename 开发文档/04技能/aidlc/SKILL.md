# AIDLC（通用版 · 不绑定具体 IDE）

本技能是 [awslabs/aidlc-workflows](https://github.com/awslabs/aidlc-workflows) 1.x 规则集的中文通用适配版：
**规则内容原样保留**在 `references/`，只重写了本文件。

**适用于任何能读文件的编码 agent** —— Codex、Claude Code、Cursor、Windsurf、Copilot、CodeBuddy、
WorkBuddy，以及自己写的 agent。不依赖某一家 IDE 的专有机制。

- 规则细则目录：`references/`（相对本文件）。文中出现的 `inception/xxx.md`、`common/xxx.md` 等路径，
  一律指 `references/` 下的相对路径。
- 规则文件是用英文写的，**对用户说话一律用中文**；规则原文里的措辞（例如阶段完成消息模板）翻译后再呈现。

### 怎么让不同 agent 都能触发这个技能

技能本身是一份说明书，**问题是 agent 怎么知道要读它**。靠项目根部的**锚点文件**：

| 你的 agent | 它会自动读的文件 | 由 `install-project-anchors.py` 生成 |
|---|---|---|
| Codex / 通用 | `AGENTS.md` | ✓ 始终生成 |
| Claude Code | `CLAUDE.md` | ✓ 始终生成 |
| Cursor | `.cursor/rules/aidlc.mdc` | 项目里有 `.cursor/` 才写 |
| Windsurf | `.windsurf/rules/aidlc.md` | 项目里有 `.windsurf/` 才写 |
| GitHub Copilot | `.github/copilot-instructions.md` | 项目里有 `.github/` 才写 |
| Trae | `.trae/rules/aidlc.md` | 项目里有 `.trae/` 才写 |
| CodeBuddy | `.codebuddy/rules/aidlc.mdc` | 项目里有 `.codebuddy/` 才写 |
| WorkBuddy | `.workbuddy/memory/MEMORY.md` | 项目里有 `.workbuddy/` 才写 |

**只有 `AGENTS.md` 和 `CLAUDE.md` 始终写，其余一律「项目里已有对应目录」才写**（2026-10-26 定）。
理由：`~/.cursor` 装过 Cursor 不代表这个项目用 Cursor；按用户主目录探测，会在别人的仓库里造出一堆
没人读的 `.windsurf/rules/aidlc.md`，还得挨个解释它们是什么。**宁可少写，不要造死文件。**

**`AGENTS.md` 是最大公约数**：它的存在就是"任何 agent 进这个目录都要先读我"。
其它几个是补充，让各家的自动加载机制也能命中。

> 没有 python 跑不了安装脚本时：把 `references/project-agents.template.md` 全文
> 复制/追加成项目根 `AGENTS.md`（带 `AIDLC:v2` 标记段即可），效果一样。

### 环境差异怎么处理

技能里只描述**意图**（"读这个文件"、"改这里"、"跑这条命令"），**不指定工具名** ——
你手上有什么就用什么（`Read` / `read_file` / `cat`，`Edit` / `str_replace` / `sed`，都行）。

| 环境差异 | 处理方式 |
|---|---|
| 没有 bash / shell | 脚本类步骤跳过，用纯文本操作代替；汇总视图不生成也不影响正确性（它只是加速阅读） |
| 没有 python | 手工兜底：锚点复制模板；生成物改为手写（但**手写的视图不入库**这条不变） |
| 有项目内记忆目录（如 `.workbuddy/memory/`） | 可以写，但**不是必需**；AIDLC 的真实来源永远是 `开发文档/` |
| 工具只能整份写文件 | 追加类操作（审计）先读写回是唯一办法 —— 但**审计绝对不允许整份覆盖**，见规则 C |

## 0. 适配层：六条硬规则（优先级高于 references 内的原始要求）

遇到冲突时，以本节为准。

### A. 提问在对话里问，不要求用户去改文件

原始规则要求把问题写进 `{phase}-questions.md`，让用户自己去编辑器填。**在本环境禁止这么做。**

正确做法：
1. 用交互式提问工具（AskUserQuestion）直接在对话中提问，每题 2–5 个可选项 + 一个开放输入；
2. 拿到回答后，把「问题 + 回答 + 时间戳」**回写**到 `开发文档/<类型目录>/CR-0X-<简称>/问题.md`；
3. 用户跳过某题时，记录 `[未答]` 并在后续按默认假设推进，同时在阶段完成消息里点明这个假设。

只有在用户主动说「给我问题清单，我自己填」时，才退化为纯文件模式。
`common/question-format-guide.md` 里的选项格式仍然要遵守（选项字母、单选、避免诱导）。

### B. 批准与继续是两个动作

阶段门禁提供三个选项（不要自创第四种）：

- **A. 请求修改**：用户提出意见 → 回到本阶段重做，重做后再次门禁；
- **B. 批准**：记录批准，但**不自动进入下一阶段**——等下一个角色回复「继续」；
- **C. 批准并继续**：记录批准并立即进入下一阶段（单人作业的默认选项）。

默认呈现 A/B/C。若本项目启用了 `approve-continue` 团队扩展（见第 5 节），则只呈现 A/B，
由下一角色显式说「继续」才推进。**单人项目不要开这个扩展**——批准与继续本是一步，拆开会变成自己批自己。

**若启用了 `role-gates` 扩展**：只有三个硬门（G1 需求定稿 / G2 设计定稿 / G3 代码合入）呈现门禁，
其余阶段不停，但必须报备一行「阶段｜产物｜自动通过」；发现要推翻已批准内容时立刻升级为硬门。
角色分工与身份判定读 `开发文档/00规则/团队配置.md`；找不到就问一次。

**若 `团队配置.md` 写了 `审批模式：全自动`**：本节 A/B/C 全部不适用——不呈现任何门禁，
按 `role-gates` 的「全自动模式」章节连续跑完，收尾交 `开发文档/<类型目录>/CR-0X-<简称>/验收报告.md`。

**若写了 `审批模式：仅需求审批`**：只在 **G1** 呈现一次门禁（需求定稿，等你批准），
批准后 G2/G3 不生效，按全自动规则跑完；G1 未批不许进设计与构建。

#### 审批模式五档（**唯一权威表**，写进 `团队配置.md` 时按此表述）

| 档位 | 门禁行为 | 适用 |
|---|---|---|
| `全自动` | **不设门禁**；四刹车（见 §5）；收尾必须交 `验收报告.md` | 小工具 / 原型 / 试验性代码 |
| `仅需求审批` | **只留 G1**；批准后 G2/G3 不生效，按全自动规则连续跑完，同样交 `验收报告.md` | **默认**；需求要人把关、实现可托付 |
| `关键三关` | G1 需求 / G2 设计 / G3 代码合入**三处硬停**，其余阶段软通过但报备一行 | 2–3 人团队，要卡设计 |
| `每阶段` | 每个阶段结束都停 | 对外交付 / 高风险 |
| `只在交付验收` | 中间不停，最后验收一次 | 极小改动 |

**三条硬规则**

1. **档位名一字不差取自上表**。不要写「三关」「仅审需求」「只批需求」「半自动」这类变体 ——
   变体无法被程序识别，也会让下一个 agent 读不懂。
2. **`团队配置.md` 的审批模式行必须保留「五档可选：`全自动`｜`仅需求审批`｜`关键三关`｜`每阶段`｜`只在交付验收`」这段清单**，
   并保留「审批模式（五选一）」整张表。**只写当前档 = 把别人的选项藏起来了**。
   > 2026-10-26 实测：新项目初始化后 `团队配置.md` 只剩「关键三关　←　G1 需求定稿 / G2 设计定稿 / G3 代码合入三处停下等批准」，
   > 五档全丢。用户后来把档位名改成 `仅需求审批`，注释还留着三关的说法 —— **档位说不停、注释说停，互相打架**。
3. **档位与门禁表必须自洽**：`仅需求审批` 就要把 G2/G3 标成「本模式不生效」，
   `全自动` 就整表换成「无门禁」，不能让读者以为不生效的门还会停。

角色切换时，在阶段完成消息里写清「本阶段由谁批准、下一阶段该谁继续」，不要把「批准」当成「授权执行」。

### C. 审计只追加，永不覆盖

原始规则反复强调这条，但通用写文件工具默认整份覆盖，**这是最容易翻车的地方**。

- 追加方式：先 Read 读末尾 → 用 Edit 在末尾插入新条目；或直接 shell 追加
  （`cat >> 开发文档/<类型目录>/CR-XXXX/审计-<人>.md`）。**一人一份**，不要写公共的 `审计.md`。
- 绝不允许「读出全文 + 拼上新内容 + 整份写回」。
- 条目必须保留用户原始输入（不概括、不改写），时间戳用 ISO 8601。

### D. 常驻加载预算

启动时**只加载**：

| 文件 | 用途 |
|---|---|
| `common/process-overview.md` | 流程总览 |
| `common/session-continuity.md` | 断点续跑 |
| `common/content-validation.md` | 写文件前的格式校验 |

`common/question-format-guide.md` 改为**第一次提问前才读**（配合规则 A，大部分内容已不需要）。
`common/terminology.md`、`overconfidence-prevention.md`、`depth-levels.md`、`error-handling.md`、
`workflow-changes.md`、`ascii-diagram-standards.md`、`welcome-message.md` 全部按需读。
**不要一次性读完 `references/`。**

### E. 产物一律中文命名

- 根目录叫 `开发文档/`，下面**五个编号目录 + 一个汇总目录**（唯一一套布局，不再有第二种）：

  ```text
  开发文档/
  ├── 00规则/      项目概述.md  团队配置.md  协作规范.md  开发规范.md  文档结构.md
  ├── 01需求/      CR-<8位号>-<简称>/   ← 需求：用户能感知的新行为
  ├── 02缺陷/      CR-<8位号>-<简称>/   ← 缺陷：与已批准预期不符（不停 G1）
  ├── 03技术债/    CR-<8位号>-<简称>/   ← 技术债：只改内部实现（停 G1）
  │                         一条 CR 一个目录，自包含（目录名就是号）：
  │       ├── 需求.md   状态.md
  │       ├── 设计/            应用设计 / 代码结构 / 工作单元 / 功能设计
  │       ├── 测试记录.md   构建说明.md   验收报告.md   问题.md
  │       ├── 运维说明.md      只有部署类 CR 才有
  │       ├── 变更说明.md      对项目级事实的影响（交付 / 存储 / 规模）
  │       ├── 决策记录.md      **为什么这么做**：选型对比 / 被否方案 / 决策人
  │       ├── 前置资源.md      **能不能做**：缺了做不了的东西（G1 前必须列）
  │       ├── 风险.md          **可能怎么失败** + 怎么知道它发生了
  │       ├── 证据/            截图 / 录屏 / 样本，供验收报告引用
  │       └── 审计-<人>.md     审计跟着 CR 走，一人一份，只追加
  ├── 04技能/aidlc/            技能副本（含 scripts/ 工具；不自带副本时省略）
  └── _汇总/                   ⚙ 本地生成·**不入库**：状态 / 需求索引 / 当前需求全貌 / 技术设计 /
                               运维说明 / 项目现状 / 决策记录 / 风险与资源 / 审计视图（9 个）
  ```

  **只有五个编号目录**：设计 / 测试 / 运维 / 审计的内容都按 CR 拆进 `CR-XXXX/`，
  全局视图由 `汇总.py` 合成到 `_汇总/`。这样两条 CR 并行时落在互不相交的路径上，**文档零冲突**。

- **规则文件里写的英文路径不作数**：`inception/requirements/requirements.md` 要落成
  `开发文档/01需求/CR-0X-<简称>/需求.md`（类型目录见下节）。映射以 `references/命名对照表.md` 为唯一权威，新建文件前查表。
- **一个文件该放哪，三步判定**：① 规则/共识（不随 CR 变）→ `00规则/`；
  ② 只属某一条 CR（需求/状态/设计/测试/验收/问题/运维/变更/决策/审计）→ `<类型目录>/CR-XXXX/`；
  ③ 跨 CR 的汇总视图 → **不手写**，跑 `汇总.py` 生成到 `_汇总/`。**没有第四步。**

  #### CR 分三类：需求 / 缺陷 / 技术债

  目录按类型分开，判据从上往下、命中即停：

  | 判据 | 类型 | 必需的主文档 |
  |---|---|---|
  | 现状与**已批准的预期不符**（本来该这样，实际不是） | **缺陷** | `问题.md`（现象/复现/影响） |
  | 动机是**用户能感知到的好处**（哪怕实现方式是换技术） | **需求** | `需求.md`（原话/范围/AC） |
  | 动机是**只有开发者能感知的好处**（可维护性 / 并行开发 / 构建速度 / 工具链），用户看到的没变 | **技术债** | `变更说明.md`（为什么动/影响面） |

  > **判据看「为什么要动」，不看「改了什么」。** 一句话自查：**没有这个需求，还会动这段技术吗？**
  >
  > - 会（纯粹因为代码该换了）⇒ **技术债**
  > - 不会（动了技术也只是为了让用户得到某个东西）⇒ **需求**
  >
  > | 例子 | 用户原话 | 判定 | 为什么 |
  > |---|---|---|---|
  > | `CR-26102200` | 把 localStorage 换成 IndexedDB，我要多个标签页改动能互相看到 | **需求** | 没有"多标签页同步"这个诉求就不会换存储 ⇒ 技术是手段 |
  > | `CR-16102100` | 改成 src 形式 | **技术债** | 用户界面一个像素都没变；动机是并行开发不冲突 ⇒ 只有开发者受益 |
  > | `CR-16102200` | 改成 vite 架构 | **技术债** | HMR、构建工具，用户感知不到 |

  三类**目录结构完全一样**，只有门禁不同：

  | 类型 | G1 | 理由 |
  |---|---|---|
  | 需求 | **硬停** | 范围由用户定，批准后才做 |
  | 缺陷 | **不停** | 事实清楚，不需要批准范围。但**修法有多种选择且影响用户时**（如"静默删还是二次确认"）临时升为需确认 |
  | 技术债 | **硬停** | 改的是"以后怎么干活"，属主动选择，该由人拍板 |

  **不属于任何需求的问题**（发现一个 bug 但跟当前 CR 无关）：在 `02缺陷/` 下建一条
  `not-started` 的 CR，只写 `问题.md`。它自然出现在状态视图的「缺陷」分组里，
  修的时候再推进状态。技术债同理。
- **设计写在 CR 里**：`CR-XXXX/设计/`（应用设计 / 代码结构 / 工作单元 / 功能设计）。
  这里的"设计"指**开发设计**，不是美术或视觉设计；视觉决策写进该 CR 的 `需求.md` 与代码。
- **目录带序号**是为了编辑器里顺序稳定（不带序号时按字符排，顺序不可预期）。
- 单位名用业务中文名（`工时统计`），不用英文 slug。
- **只约束文档**：代码文件名仍按语言惯例（`.ts` `.py` `.js`），不要把代码文件也中文化。
- **一律中文**：不保留英文目录，也不按阶段分目录。

### F. Git 提交：不主动提交，不整盘 add

**默认不提交。** 改完文件就停下，说清楚「改了哪几个文件、为什么」，等用户明确说「提交」再动。

提交是不可逆动作，而且最容易把「用户自己的改动」和「agent 的改动」混在一起。
用户看着工作区，比你更清楚什么时候该落盘。

| 规则 | 说明 |
|---|---|
| **禁用 `git add -A` / `git add .`** | 必须按路径精确 add。工作区里可能有用户正在改的东西 |
| **一个提交只做一件事** | 技能改造 / 需求文档 / 代码实现，分三次提交，不合并 |
| **提交前先看 `git status`** | 确认清单里没有不该出现的文件 |
| 用户明确要求时（「做完提交」「帮我 commit」） | 可以提交，但上面三条照样守 |

> **真实事故（2026-10-22）**：改完技能后习惯性 `git add -A`，把用户同时在做的整套 CR
> （`serve.py` + 两个 bat + 13 个文档，927 行）混进了「修文档」那个提交里 ——
> commit message 说的是"修取号流程"，内容九成是用户的东西。事后 `reset --soft` 才拆开。

**用户没明说时，只有这三个节点该提交**：

1. G1 批准、开始实现 —— 需求定稿该落盘
2. CR 交付 —— 代码 + 文档 + 测试记录一起
3. 用户说「验收通过」

**其余时候**：改完就停。让用户在 `git status` 里看到改动 —— 他扫一眼就知道你干了什么，
比任何 commit message 都直观。

## 1. 启动

> **硬规则（优先级最高）**：先看工作区有没有 `开发文档/状态.md`。
> 有 ⇒ 这是进行中的 AIDLC 项目，**用户的任何新需求都按迭代处理**，不许问「要不要走 AIDLC」，
> 也不许因为「这次改动很小」就直接写代码。没有 ⇒ 才按新流程或普通对话处理。
>
> 历史事故（2026-10-18，CodeBuddy）：用户只说「部署到线上，能发个链接给同事」，技能因描述缺少
> 上下文触发条件被判为不适用，直接生成代码、跳过全部门禁。本规则与新增的描述条件就是为堵这个洞。

**0. 新建项目（还没有 `开发文档/`）先跑初始化脚本 —— 只写入口文件不算初始化。**

> 2026-10-26 真实事故（uino-opc/opcapp）：用户说「初始化项目，入口用 CLAUDE.md，不要改 AGENTS」，
> agent 只生成了一个 6 KB 的 `CLAUDE.md` 就宣布完成，`开发文档/` **一个目录都没建**，
> 还得用户回头问「为什么没初始化开发文档」。根因：建布局这件事只写在散文里，漏一步不报错。

```bash
python <技能>/scripts/初始化.py <项目根> --entry claude   # 只写 CLAUDE.md，AGENTS.md 一字不动
python <技能>/scripts/初始化.py <项目根> --entry claude --full-entry   # 规范全文写进 CLAUDE.md
python <技能>/scripts/初始化.py <项目根>                  # 常规：自动探测各平台
python <技能>/scripts/初始化.py <项目根> --dry-run        # 只说要做什么
python <技能>/scripts/初始化.py <项目根> --refresh-templates  # 只把规则文件的「模板头」改成本项目格式
```

> **`--full-entry`**：默认入口文件只放一句「先读 AGENTS.md / 开发文档」的指针；
> 加了它就放**全文规范**。用于「项目自己的 AGENTS.md 不许改，AIDLC 规矩只能落在 CLAUDE.md」的场景 ——
> 否则 CLAUDE.md 里的指针会指向一个根本没有 AIDLC 段的 AGENTS.md。

| 它做什么 | 落点 |
|---|---|
| 六个编号目录 | `开发文档/{00规则,01需求,02缺陷,03技术债,04技能,_汇总}` |
| 四份规则文件（从模板**整份复制**） | `00规则/{项目概述,团队配置,开发规范,文档结构}.md` |
| 状态骨架 | `开发文档/状态.md` |
| 技能副本（项目自包含） | `开发文档/04技能/aidlc/` |
| 入口锚点 | 由 `--entry` 决定（见下） |
| git 钩子 + `.gitattributes` LF 保护 | `core.hooksPath` → `04技能/aidlc/scripts/hooks` |
| `_汇总/` 视图 + 自检 | 有 CR 才生成视图；自检结果直接打出来 |

**`--entry` 怎么选**

| 取值 | 写什么 | 什么时候用 |
|---|---|---|
| `auto`（默认） | 自动探测，命中的平台都写 | 常规新项目 |
| `claude` | **只写 `CLAUDE.md` 的指针段，`AGENTS.md` 一字不动** | 上游仓库自有 `AGENTS.md`、明确说了不许改 |
| `agents` | 只写 `AGENTS.md`（全文约定） | 只认 AGENTS 的 agent（Codex 等） |
| `cursor` / `windsurf` / `copilot` | 对应规则文件 | 单一 IDE |
| `none` | 不写锚点 | 只想建目录 |

**没有任何锚点 = 技能不会被触发**，这一步不能省；`--entry claude` 只是换入口，不是不装。
脚本幂等：已存在的规则文件和用户原文都不覆盖，重跑只会补缺。

1. 检查项目根是否有 `开发文档/状态.md`：
   - 有 → 读它 + `common/session-continuity.md`，**续跑**上次阶段，不要重新开流程；
   - 没有 → 新流程。

   1b. **维护项目根 `AGENTS.md`** —— 把「必须走 AIDLC」钉在项目上，而不是只靠技能被加载：

   **首选：跑脚本**（幂等，不覆盖原文）

   ```
   python scripts/install-project-anchors.py <项目根> --with-skill
   ```

   - `--with-skill` 会把技能**复制一份到项目内 `开发文档/04技能/aidlc/`**，让项目自包含：换机器、换 agent、
     别人接手都能跑，不依赖宿主装没装。**建议新项目一律带上**；只想写锚点就不加这个参数。

   - 它会自动探测本机在用哪些平台，把带 `AIDLC:v2` 标记的规则块写进各自的**项目记忆 / 项目规则**：
     `AGENTS.md`（始终）、`CLAUDE.md`、`.cursor/rules/aidlc.mdc`、`.windsurf/rules/aidlc.md`、
     `.workbuddy/memory/MEMORY.md`、`.github/copilot-instructions.md`；项目里已有 `.codebuddy/` 才写它。
   - `--dry-run` 先看会改哪些文件；`--remove` 只删标记段，用户原文逐字节还原；
     `--platforms agents,claude,cursor` 可指定，跳过自动探测。
   - 脚本按 **`<!-- AIDLC:v1 BEGIN --> … END -->`** 定位：不存在就追加，存在就整段替换，已是最新就报 `unchanged`。
   - 行尾自动跟随目标文件（CRLF / LF），不会把整文件行尾翻掉。

   **没有 python 时手工兜底**：把 `references/project-agents.template.md` 全文复制/追加成项目根 `AGENTS.md`，
   规则同上——**绝不覆盖用户原文**，只在末尾追加或整段替换标记区间。

   只做一次。后续迭代脚本会报 `unchanged`，不要每轮重写。

   > **为什么要这一步**：技能靠 description 文本匹配触发，用户不点名就可能不加载——2026-10-18 的
   > 部署事故就是这么发生的。`AGENTS.md` 是**项目级锚点**：任何 agent 进入这个目录都会先读它，
   > 与「哪个 agent、说没说到 AIDLC」无关。这是唯一不依赖措辞的触发方式。
   1c. **判断是否多人并行** —— 出现下列任一情况，**先读 `common/parallel-collaboration.md`** 再动手：

   - `开发文档/*/` 下有多个 `CR-*` 目录（类型目录里）；
   - `团队配置.md` 写的成员数 > 1；
   - `git branch` 里除 `main` 外还有 `iter/*` 分支；
   - 用户提到「两个人」「同事」「并行」「各做各的」。

   **取号 = 建 CR 目录，不需要额外的「号段」文件。**

   号的构成（8 位，**算出来的，不用抢**）：

   ```
   P Y MMDD N
   │ │ │    └─ 当天第几个（00~99）
   │ │ └────── 月日
   │ └──────── 年（末位，2026 → 6）
   └────────── 人编号（`团队配置.md` 里定，一人一位，分配后不改）
   ```

   | 谁 | 日期 | 第几个 | 号 |
   |---|---|---|---|
   | 张勇（人 1） | 2026-10-21 | 00 | **16102100** |
   | 张勇（人 1） | 2026-10-21 | 01 | 16102101 |
   | 李四（人 2） | 2026-10-21 | 00 | **26102100** |
   | 张勇（人 1） | 2027-10-21 | 00 | 17102100 |

   **取号三步，第一步必须是 `git pull`：**

   1. **`git pull`** —— 拿到所有人已占的号，**包括你自己在别的电脑上占的**；
   2. 扫 `<类型目录>/CR-<P><Y><MMDD>*/`（**含类型那层**），**N = 已有目录的个数**（从 00 起：一个都没有取 00，已有一个取 01）；
   3. 建 `<类型目录>/CR-<P><Y><MMDD><N>-<简称>/`，**至少放一个 `状态.md`**（阶段 `not-started` 也行）
      → `commit` → **`push`**。

   **目录名就是占位凭据**：同号必然撞同一路径，合并时当场暴露。
   不需要再建「号段文件」—— 那是号还要「抢」的年代留下的；8 位号算得出来，一份文件只为了记「这个号有人用了」，
   而**目录名本身已经说明了这件事**（CR 里也有提出人、时间、原话、号段）。

   **push 被拒不是异常，是竞争仲裁的正常结果**：`pull` → 重算 N → 再推。

   > 最典型的就是「同一个 git 账号在多台电脑登录」：人编号相同（本来就是同一个人，这是对的），
   > 但两台机器各自数到「当天 0 个」，都取 00 —— 先推的占住，后推的 pull 一下改成 01。
   > **所以 `pull` 不能省。只扫本地就取号，在多机或共用账号时必然撞。**

   **两个人共用一个 git 账号时**（外包、临时同事）：人编号会重复，审计也分不清谁做的。
   优先给各自配独立 email；实在不行，在启动前设环境变量 **`AIDLC_PERSON=2`** 覆盖人编号 ——
   技能优先读它，读不到才看 `git config user.email` 查表。

   **一天最多 100 个**（序号 00~99，从 00 起）。不够用再加一位。

   **FR / AC 号段**：新 CR 从 **CR 内 `FR-01` 起**，不再全局递增；跨 CR 引用一律写
   `CR-16102100/FR-01`。这样两条 CR 各自的 FR-01 不会撞（10-21 撞的就是 13~16 vs 13~15）。
   老 CR 的全局编号**不迁**，历史文档保持原样。

   **轮次号 `R` 只用于展示，唯一标识一律用 `CR-<8位号>`。**
   不要往 `状态.md` 里写占号记录——那是共享单文件，并发写必冲突。

   > 历史事故一（2026-10-21，试点1）：两条并行线都编成 R7（CR-7 / v1.7 / §2.11），合入时 19 处冲突，
   > 需求编号 FR-48~ 完全重叠，只能整条线重编为 R8。根因是「序号被当成标识用」。
   > 历史事故二（2026-10-21 晚，试点2）：两条线都取 CR-2，**号段文件按短名命名，两个文件并存、撞号完全静默**，
   > 直到合并才发现：CR 号、FR 段（13~16 vs 13~15）、AC 段全部重叠，只能把后到的那条整条重编为 CR-3。
   > **根因不是人不守规矩，是「占号」在文件层面不可见** —— 所以文件名必须由号决定，同号必然撞同一路径。

   1d. **确认布局** —— 布局由本技能规定（见第 E 节），**不需要每轮重新决定**。
   要做的只是读一眼 `开发文档/00规则/文档结构.md`：

   - **存在** ⇒ 读它，取**项目级补充**（本项目额外放了什么、哪些文件是生成物）。
   - **不存在** ⇒ 按本技能布局建，并把 `00规则/文档结构.md` 由模板复制出来（`references/文档结构.template.md`）。

   布局长这样：

   ```text
   开发文档/
   ├── 00规则/      项目概述.md  团队配置.md  协作规范.md  开发规范.md  文档结构.md
   ├── 01需求/      CR-<8位号>-<简称>/
   ├── 02缺陷/      CR-<8位号>-<简称>/
   ├── 03技术债/    CR-<8位号>-<简称>/   每条含：需求/问题/变更说明 状态 设计/ 测试记录
   │                         验收报告 运维说明 变更说明 审计-<人>
   ├── 04技能/      本项目的技能副本（含 scripts/ 工具）
   └── _汇总/       9 个视图（本地生成·不入库）
   ```

   **目录带序号是为了编辑器里顺序稳定**。`04技能/` 不是必须的——项目不自带技能副本时省掉它。
   **没有独立的设计 / 测试 / 运维 / 审计目录**：这些内容都按 CR 拆进 `CR-XXXX/`。

   **验流程本身的用例不放 `开发文档/`**：它验的是 AIDLC 这个流程，不是本项目需求，
   放在项目根（如 `流程测试用例.md`），与 `开发文档/`（项目档案）区分开。`开发文档/` 只装项目档案。

   **分片入库，视图不入库**（2026-10-21 定的，别改回去）：

   | 文件 | 入库？ | 谁写 |
   |---|---|---|
   | `<类型目录>/CR-XXXX/{需求,状态,设计/*,测试记录,构建说明,验收报告,问题,运维说明,变更说明,决策记录,前置资源,风险}.md` | **要** | 人 / agent，**一条 CR 一个目录** |
   | `<类型目录>/CR-XXXX/证据/`（截图 / 录屏 / 样本） | **要**（单文件 ≤ 5 MB；更大走 git LFS） | agent 抓取或人贴图 |
   | `<类型目录>/CR-XXXX/审计-<人>.md` | **要** | 各人只写自己那份，只追加 |
   | `开发文档/_汇总/`（9 个视图） | **不要**（`.gitignore` 整目录） | 只有 `scripts/汇总.py`，本地生成 |

   为什么：视图是**扫分片算出来的**。两条并行线各跑一次汇总，内容必然不同（各自多一行 CR、
   生成时间也不同），入库就会在合并时三方冲突；而手工解冲突毫无意义——正确结果只能重算。
   实测（2026-10-21 试点2）：改成这条规则前，一次合并里 `状态.md` 冲突 5 处、`需求索引.md` 3 处、`应用设计.md` 1 处、`构建汇总.md` 1 处，**全是共享单文件**；改成「按 CR 拆目录 + 视图本地生成」后，同样场景**冲突数 0**。
   **分片入库保证可追溯，视图不入库保证不冲突。**

   #### 决策记录（`CR-XXXX/决策记录.md`）—— 别让它变成空白文件

   只在一个条件下写：**有取舍**。没有备选方案的事不用记（"加个按钮"不需要决策记录）。

   每条决策五样东西，缺一不可：

   ```markdown
   ## 2026-10-22T06:55 · CR 编号规则

   - **背景**：要 6 位、绝对不冲突、带时间，三者不能同时满足
   - **选项**：MMDD+序号 / Unix 时间戳 / ULID / 人+年+月日+序号
   - **决定**：人+年+月日+序号，8 位
   - **理由**：首位是人 ⇒ 两人永不共享号段；年位解决跨年；仍能口头引用
   - **被否**：ULID 绝对唯一，但 26 字符没法口头说「把 CR-01JBX4K2… 看一下」
   ```

   **只记结论和理由，不要抄对话原文** —— 全量对话八成是试错过程，结论、理由、被否的选项才是能复用的。
   被否掉的方案尤其重要：半年后有人问"当初为什么不直接用现成的 X"，答案在这里。

   `汇总.py` 会把各 CR 的决策记录合成 `_汇总/决策记录.md` —— **项目复盘、交接、交付汇报先看这份**。

   #### 前置资源（`CR-XXXX/前置资源.md`）—— G1 之前必须列

   回答「**能不能做**」。缺模型、缺设计图、缺 API Key、缺目标设备 —— 这些不列出来，
   批准了也是干等；等发现做不了时，需求已经批过一轮，返工的不只是代码。

   ```markdown
   | 资源 | 类型 | 必需性 | 状态 | 谁提供 / 在哪 | 替代方案 |
   |---|---|---|---|---|---|
   | 主建筑模型 glb | 素材 | 必需 | 待提供 | 客户 3D 组，下周 | 先用占位盒体走通交互 |
   | 目标机显卡型号 | 环境 | 必需 | 已有 | GTX 1660 / 集显 UHD630 | — |
   ```

   - **状态四选一**：`已有` / `待提供` / `可替代`（**必须填替代方案**）/ `不适用`
   - **类型七类**：资料 · 素材 · 账号与权限 · 环境 · 数据 · 人 · 预研结论

   **G1 前的硬要求**：`必需 + 待提供` 的项**逐条摆给用户**，让他选「等 / 用替代 / 缩小范围」；
   **不许在没列清单的情况下说"可以开工"**。结论写进 `需求.md` 的 `- 范围依据：` 或 `决策记录.md`。

   > 为什么不写进 `需求.md`：需求一批准就冻结，而资源状态**会变**（今天待提供、明天已有）。
   > 写进已批准文件等于逼人改历史。

   #### 风险（`CR-XXXX/风险.md`）—— 关键是「怎么知道它发生了」

   回答「**可能怎么失败**」。四条核心字段：可能性 / 影响 / **触发信号** / 应对。

   ```markdown
   | 编号 | 风险 | 可能性 | 影响 | 触发信号 | 应对 | 负责人 | 状态 |
   |---|---|---|---|---|---|---|---|
   | R-01 | 面数超预算，目标机掉到 20 帧以下 | 高 | 高 | 帧率面板连续 3 秒 < 30 | 做 LOD；超预算砍非主视角模型 | 张勇 | 待处理 |
   ```

   **触发信号写不出来 ⇒ 这个风险你还没想清**，只是抄了个名词。
   状态含 `已接受`（正当结论，但要在应对里写清为什么接受：成本 > 损失）。

   **不要写**：确定会发生的事（那是任务）· 已发生的事（那是 `问题.md`）· "需求可能变"（太笼统）。

   > 三份文件的分工别混：`问题.md` = 需求澄清问答；`测试记录.md` 的"未覆盖风险" = 测试档位的代价；
   > `风险.md` = 这件事可能翻车的地方。

   **细则格式、七类资源、反面例子**见 `references/common/risk-and-resources.md`。
   `汇总.py` 把两者合成 `_汇总/风险与资源.md`（**开工前和交付前的检查单**）；
   `自检.py` 查两条：必需资源「待提供」但 CR 已开工 → **判错**；高风险仍「待处理」→ 建议。

   #### 基线 vs 增量（`需求性质`）+ 当前需求全貌

   每条 CR 的 `需求.md` 头部有一个字段，回答「这条是**第一版需求**还是**后来加的**」：

   ```markdown
   - 需求性质：基线      # 第一版（v1.0 那批），全项目**有且仅有一条**
   - 需求性质：增量      # 基线之后追加的需求 / 技术债 / 其它改动
   ```

   - **只有基线需要显式写**，不写就按 `增量` 算 —— 基线是少数，增量是常态。
   - 缺陷 CR 没有 `需求.md`，不参与这个字段（它记的是「与已批准预期不符」，不是需求）。
   - `自检.py` 会检查**基线有且仅有一条**：0 条 → 提醒补；多于 1 条 → 判错（否则全貌排序失真）。

   **为什么要它**：目录名 `CR-00-初始版本` 只能靠"看名字"认出基线 —— 机器不认识，
   视图也看不出来。有了字段，`_汇总/需求索引.md` 多一列「性质」，`_汇总/当前需求全貌.md`
   能把**基线 + 全部增量**按演进顺序拼成一份。

   **`_汇总/当前需求全貌.md` 回答什么**：*「这个系统现在一共要满足什么」*。

   单条 CR 只回答「这次改了什么」；要答"总计"就得把基线和 N 条增量拼起来读。这个视图就是
   拼好的结果 —— 顶部一张清单（性质 / 编号 / 摘要 / FR 号段），下面按「基线 → 增量」贴全文。

   **总览一律靠视图生成，不靠手工维护活文档。**

   #### 领域补充（`references/domains/`）—— 按需加载，不进主流程

   主流程对任何项目都一样，但有些领域有额外的必备文档：

   | 领域 | 文件 | 补什么 |
   |---|---|---|
   | 三维 / WebGL / 数字孪生 | `domains/3d-visualization.md` | 资产清单（含许可）、性能预算（含设备基线）、**前置资源：模型/设计图/目标设备**、视觉验收证据、**大资产走 LFS** |
   | Agent / LLM 应用 | `domains/agent-app.md` | prompt 版本、tool schema、**eval 用例集与通过率**、成本与模型版本锁定、**前置资源：至少两个可用模型 + key/额度** |
   | 服务端 / API | `domains/backend-service.md` | **接口契约**（错误码/幂等/分页语义）、数据迁移与回滚、多环境矩阵 |
   | CLI / 工具类 | `domains/cli-tool.md` | **命令契约**（退出码/幂等/副作用）、stdout 与 stderr 分离、破坏性命令的 dry-run |

   开工先跑一次 `汇总.py` 生成最新视图再读，否则读到的是过期表格。
   若某项目早期把视图提交过，脚本会提示 `git rm --cached`；跑一次 `安装钩子.py` 会补 `.gitignore`。

   本技能 `scripts/` 目录里的五件工具（**跟着技能走，项目里不用另建 `工具/`**）：

   | 脚本 | 作用 |
   |---|---|
   | `scripts/初始化.py` | **新项目第一件事**：建六个编号目录 + 四份规则文件（整份复制模板）+ 状态骨架 + 技能副本 + 入口锚点 + git 钩子；`--entry claude` 时只写 CLAUDE.md、不碰 AGENTS.md |
   | `scripts/汇总.py` | 扫各 `<类型目录>/CR-XXXX/*` 分片，重建 `_汇总/` 下 9 个视图（状态/需求索引/当前需求全貌/技术设计/运维/项目现状/决策记录/风险与资源/审计） |
   | `scripts/安装钩子.py` | 设 `core.hooksPath` 指向 `scripts/hooks/`；补 `.gitattributes` 的 LF 保护与 `.gitignore` 的 `_汇总/` 排除 |
   | `scripts/自检.py` | 体检 14 类：锚点 / 副本位置 / 钩子 / `.gitattributes` / 布局 / **规则文件**（五档清单有没有被简写）/ 生成物 / 编号 /
     基线 / **前置资源**（缺资源就开工）/ **风险**（高风险未处理）/ **死规则**（字段全项目 0 使用）/
     **孤儿 CR**（汇总会静默跳过）/ 技能自洽 |
   | `scripts/预览.py` | 生成 `_汇总/index.html` + `_sidebar.md` 并起本地服务，用 Docsify 看文档（资源自带，**不连 CDN**） |
   | `scripts/hooks/` | `post-merge` / `post-commit`（父提交数=2）/ `post-rewrite` + `_summary.sh` |

   **钩子只做两件事**：重建 `_汇总/` 视图；若 `团队配置.md` 里声明了 `- 构建命令：xxx`，再执行它。

   > 为什么构建命令要由项目声明、而不是技能写死：AIDLC 适用于前端 / 后端 / CLI / 纯文档各种项目，
   > 构建可能是 `npm run build`、`cargo build`、`make`，也可能根本不存在。**技能不猜，项目说做什么就做什么。**
   > 拼装型项目（产物由源码生成）**应该**配这一行 —— 否则 git 会把产物"自动合并"成半对半错的内容，
   > 而且不报冲突（2026-10-22 实测：两条 CR 分叉合并后，产物与重建结果差 362 行，`git merge` 却说成功）。

   #### 给技能加脚本时的五条（都是踩过的）

   1. **会被别的脚本 import 的模块，必须在 import 前设 `sys.dont_write_bytecode = True`。**
      否则 Python 在 `scripts/__pycache__/` 写 `.pyc`，文件名带版本号（`cpython-311` / `313`），
      多机不同版本会各自生成、一旦入库互相污染；`cp -r` 同步副本时还会扩散。
      `.gitignore` 里也要有 `__pycache__/`、`*.pyc` 兜底。
   2. **`subprocess` 一律写 `encoding='utf-8', errors='replace'`，不要用 `text=True`。**
      Windows 下 `text=True` 按 locale（cp936）解码 git 的 UTF-8 输出，
      中文路径会变成乱码，再交给 `cwd=` 就是 `WinError 267`（目录名无效）。
   3. **靠「往上找 `开发文档/`」定位项目，不写死相对路径。** 脚本放在 `scripts/`、
      `开发文档/工具/` 还是哪都能跑；用 `cwd` 优先、脚本位置兜底。
   4. **钩子里跑的脚本，任何失败都不能阻塞 git。** 汇总挂了顶多视图过期，合并必须继续。
   5. **改结构时同步改脚本里的文案。** 自检的「技能自洽」只扫旧**目录名**，
      扫不到「重建 状态.md / 需求索引.md」这种写在 print 里的旧描述 —— 这类只能人肉记住。

   **开工先跑一次自检**（约 1 秒）：

   ```
   python <技能副本>/scripts/自检.py        # 全绿 → exit 0；有真问题 → exit 1
   python <技能副本>/scripts/自检.py --fix  # 只补 .gitattributes（幂等）
   ```

   > **为什么要有这一步**：规则写在 SKILL.md 里，但**规则不会自己执行**。2026-10-21 一天内踩到两个
   > 同类问题——技能副本落到项目根 `skills/`、装钩子不写 `.gitattributes`。共同点是「本机能跑、
   > 换台机器静默失效、**而且不报错**」。这类问题只能靠主动体检发现，靠人记住是不行的。
   > 自检报 ✗ 就按它给的「└」修，别自己发明修法。

   项目若自带技能副本（固定位置 `开发文档/04技能/aidlc/`），直接跑副本里的脚本；
   没有副本时才用宿主技能目录里的。**别把脚本单独复制成项目里的 `工具/` 目录** —— 那是重复维护。

   #### 文档预览（可选）：把 `开发文档/` 当站点看

   ```bash

   python <技能副本>/scripts/预览.py --host 0.0.0.0  # 同一内网的同事也能看
   python <技能副本>/scripts/预览.py --no-serve      # 只生成入口，不起服务
   ```

   `_汇总/` 是**自包含**的，整个目录可以打包拷走：

   ```
   _汇总/
   ├── index.html      入口（全是相对路径，不依赖外部）
   ├── _sidebar.md     侧边栏：9 个视图 + 三类 CR 的文档树

   ├── vendor/         docsify.min.js + vue.css（从技能 assets 复制）

   ```

   打包后对方只需要：`cd _汇总 && python -m http.server 8090`，浏览器开 `127.0.0.1:8090`。
   **本脚本的服务根就是 `_汇总/`**，所以用它起和用系统 `http.server` 起，效果完全一样。

   **渲染引擎是本地化的 Docsify**（`assets/docsify.min.js` + `assets/vue.css`，共 ~170 KB）。
   **不要改成从 CDN 加载**：内网/断网时会白屏，而且**没有任何报错** —— 这是本项目最典型的运行环境。
   **也不要改成"从技能目录读 engine"**：那样 `_汇总/` 就不自包含，打包出去必坏。

   ⚠ `docs/` 是**快照**：改了源文档要重跑本脚本，否则包里的 CR 原文是旧的。
   视图（`状态.md` 等）也是快照，同样要重跑 `汇总.py`。

   > 为什么不把预览塞进 `汇总.py`：起服务是**阻塞**操作，放进汇总会让 git 钩子卡死。
   > 汇总只管生成，看是另一件事，用的时候再起。

   **`团队配置.md` / `协作规范.md` / `文档结构.md` 的规范位置是 `开发文档/00规则/`**，只读这里、只写这里。

   **多人并行时额外一步**：读 `00规则/协作规范.md`（没有就读 `common/parallel-collaboration.md`），
   按 8 位号规则建 `<类型目录>/CR-<P><Y><MMDD><N>-<简称>/` 取号（**目录名就是号**）。详见 `common/parallel-collaboration.md`。

   > 为什么布局要写死（2026-10-21，待办清单项目）：先前允许「项目自定义布局」，结果工具和文档各认一套，
   > `汇总.py` 直接报「没有可汇总的需求目录」。**布局只有一套，代码和文档才不会打架。**
   > 若 agent 不读布局，下一轮会另造一套目录，两套结构并存比不拆更乱。

## 2. 三阶段路由

阶段是否执行由「项目状态 + 需求性质」决定，不要求用户记命令。判断依据写在每个阶段条款里。

### 🔵 INCEPTION（做什么、为什么）

| 阶段 | 何时执行 | 规则文件 |
|---|---|---|
| 工作区检测 | 总是 | `inception/workspace-detection.md` |
| 逆向工程 | 存量项目且无逆向产物 | `inception/reverse-engineering.md` |
| 需求分析 | 总是（深度按 minimal/standard/comprehensive 自适应） | `inception/requirements-analysis.md` |
| 用户故事 | 影响最终用户、多角色、需验收标准时 | `inception/user-stories.md` |
| 工作流规划 | 总是 | `inception/workflow-planning.md` |
| 应用设计 | 需要新组件/服务层/接口定义时 | `inception/application-design.md` |
| 单元拆分 | 需要拆成多个工作单元时 | `inception/units-generation.md` |

### 🟢 CONSTRUCTION（怎么做）

逐单元循环，一个单元的设计与代码做完再进下一个：

| 阶段 | 何时执行 | 规则文件 |
|---|---|---|
| 功能设计 | 新数据模型、复杂业务规则 | `construction/functional-design.md` |
| NFR 需求 | 有性能/安全/扩展性/技术栈选型 | `construction/nfr-requirements.md` |
| NFR 设计 | 上一步执行了 | `construction/nfr-design.md` |
| 基础设施设计 | 涉及部署架构、云资源 | `construction/infrastructure-design.md` |
| 代码生成 | 每个单元总是执行（先计划→批准→生成） | `construction/code-generation.md` |

全部单元完成后：**构建与测试** → `construction/build-and-test.md`。
**按 `团队配置.md` 的「测试策略」执行，默认 `仅静态`**（见下）。

#### 测试策略（三档，写在 `团队配置.md`）

| 档位 | 做什么 | 不做什么 | 准入条件（**三条全满足**才可降到该档） |
|---|---|---|---|
| `全量` | 新增用例 + 跑全量回归 + 人工走查清单 | — | 默认建议档：有持久化数据 / 有数据迁移 / 会多轮迭代 |
| `仅回归` | **不新增**用例，但必须跑**既有全部**用例 | 不设计新测试 | 不碰数据模型、不碰渲染层结构 |
| `仅静态` | 语法检查、静态扫描、构建校验；人工自测一遍主流程 | **不写也不跑自动化用例**（含回归、含数据类改动） | 默认档；用户可随时改成 `全量` 或 `仅回归` |

**四条硬约束（任何档位都成立）**

1. **档位由用户在 `团队配置.md` 定，agent 不得按改动类型自行升档**。
   `仅静态` 就是**绝对不跑**——即使本次是持久化数据、数据迁移、存储层替换，**也不破例、不提示升档、不再询问**
   （2026-10-21 用户明确要求：「绝对不跑，别问」）。
2. **降档必须留痕**：`验收报告.md` 写明「本轮策略＝仅静态，未做自动化测试」，以及**因此未覆盖的风险**。
   测试可以省，「我知道这里没验证」不能省。
3. **静态检查不能宣称「测试通过」**：语法过了不等于行为对。报告里只能写「静态检查通过」。
4. **档位标签必须与实际动作一致**：新增了用例就记 `全量`；只跑了既有的记 `仅回归`；
   一旦实际动作超出所标档位，改标并说明——**写「仅回归」却新增用例属于记录失真**。

> **代价（用户已知悉并选择接受）**：数据类改动在 `仅静态` 下**没有任何自动化保护**。历史参照：R6 的
> localStorage → IndexedDB 迁移是靠 74 条用例才发现字段级问题；同类改动在 `仅静态` 下只能靠人工验收。

### 🟡 OPERATIONS

占位阶段（`operations/operations.md`），当前只做说明，不产出实际运维动作。

> **⚠️ 部署 / 上线不是例外，也不是「顺手做一下」**
>
> 「占位阶段」指的是**本流程不定义运维阶段的做法**，**不是**「部署请求可以不进流程」。
> 用户说「部署到线上」「发个链接给同事」「发布一下」时，它仍然是一次**变更请求**，必须：
>
> 1. 登记 CR（哪怕只有一句话）；
> 2. 补需求增量：部署目标、访问方式、数据影响（如 localStorage 按 origin 隔离，换域名会不会丢数据）、回滚办法；
> 3. 按项目当前审批模式过门禁（`全自动`也要留痕，`仅需求审批`至少过 G1）；
> 4. 写审计。
>
> **禁止**：跳过以上直接生成 `.deploy/` 脚本或 `dist/` 产物。
>
> 历史事故（2026-10-18，CodeBuddy）：用户只发「部署到线上，能发个链接给同事」，AI 直接产出
> `.deploy/start-lan.ps1` 与 `dist/index.html`，**审计、CR、门禁三样全无**，事后要靠翻 git 才知道做过什么。

```
  → 按规则执行（提问走规则 A）
  → 产出写入 开发文档/（中文命名，见命名对照表）
  → 更新 aidlc-state.md（执行/跳过、当前阶段）
  → 呈现阶段完成消息 + 门禁三选项（规则 B）
  → 用户选 A：重做；选 B：停在这里等「继续」；选 C：进下一阶段
  → 记录用户原始回答（规则 C）
```

**不要自行发明导航选项**（原规则明确禁止 3 选项以上的「涌现行为」）。除了 A/B/C 门禁，
不要在阶段之间插入「你想先看哪个」之类的自由菜单。

## 4. 产物目录（中文命名）

写在**用户项目**里，不是技能目录。**目录名、文档文件名一律用中文**，
完整对照见 `references/命名对照表.md`（规则文件里的英文路径按那张表映射）。

```text
<项目根>/
├── [应用代码]                    # 代码永远在这里，文件名按各语言惯例，不要中文化
├── AGENTS.md                     # 入口锚点（必须留在根，挪走就没人读）
└── 开发文档/                     # 只放文档
    ├── 00规则/                   # 项目概述.md 团队配置.md 协作规范.md 开发规范.md 文档结构.md
    ├── 01需求/                   # 需求：用户能感知的新行为
    ├── 02缺陷/                   # 缺陷：与已批准预期不符（不停 G1）
    ├── 03技术债/                 # 技术债：只改内部实现（停 G1）
    │   └── CR-XXXX-<简称>/       # 一条 CR 一个目录，自包含（目录名就是号）：
    │                             #   需求 / 状态 / 设计/ / 测试记录 / 构建说明 /
    │                             #   验收报告 / 问题 / 运维说明 / 变更说明 /
    │                             #   决策记录 / 前置资源 / 风险 / 证据/ / 审计-<人>
    ├── 04技能/aidlc/             # 技能副本（含 scripts/ 工具；不自带副本时省略）
    └── _汇总/⚙                   # 9 个视图，本地生成、不入库
```

**没有独立的设计 / 测试 / 运维 / 审计目录** —— 这些内容都按 CR 拆进了 `<类型目录>/CR-XXXX/`，
全局视图由 `汇总.py` 合成到 `_汇总/`。

典型文件名（都在 `CR-XXXX/` 下）：`需求.md`、`状态.md`、`设计/应用设计.md`、
`设计/业务规则.md`、`设计/代码结构.md`、`测试记录.md`、`构建说明.md`、`验收报告.md`、
`问题.md`、`运维说明.md`、`变更说明.md`、`决策记录.md`、`审计-<人>.md`。

`{单元}` 用业务名（`工时统计`、`登录鉴权`），不要用 `timesheet-api` 这类英文 slug。

硬约束：代码不进 `开发文档/`；`开发文档/` 里不写可执行文件。
是否纳入 git 由用户决定（默认建议纳入，它就是审计载体）。

## 5. 扩展

启动时**递归扫描** `references/extensions/**/*.opt-in.md`，只读这些轻量文件，**不读完整规则**。
把每个 opt-in 问题在需求分析阶段问用户（规则 A），答案写进 `aidlc-state.md` 的扩展配置表。

- 用户选「用」→ 到对应阶段才读完整规则文件（同名去掉 `.opt-in`）；
- 用户选「不用」→ 完整规则永不进上下文；
- **没有 `.opt-in.md` 的扩展视为常开**，启动即读。

已有扩展：

| 扩展 | 作用 |
|---|---|
| `extensions/security/baseline/` | 安全基线（鉴权、密钥、输入校验等硬约束） |
| `extensions/testing/property-based/` | 基于属性的测试（PBT），防 AI 改代码迁就测试 |
| `extensions/team/role-gates/` | 角色门禁：停几处由 `团队配置.md` 的档位决定（默认只留 G1），其余阶段软通过但报备；含 PO/DEV/REV 四眼原则 |
| `extensions/team/approve-continue/` | 团队模式：门禁只留 A/B，批准后必须由下一角色说「继续」 |
| `extensions/team/audit-signature/` | 审计签名：每条 audit 记录带 `User` / `Email`（取自 `git config`） |
| `extensions/team/doc-sync/` | 文档同步：代码改动后强制回写受影响的阶段文档 |

启用的扩展是**硬约束**，不是建议；不适用的规则在阶段完成消息里标 N/A，不适用不算违规。

### 预设组合（新建项目时先选一个，别逐项调）

| 预设 | 适用 | **审批模式**（写进 `团队配置.md` 的就是这五个字） | approve-continue | audit-signature | doc-sync |
|---|---|---|---|---|---|
| **单人** | 一个人从头做到尾 | `仅需求审批`（试点结论：单人跑三关每道门来回三次，摩擦过大） | **关** | 开 | 仅关键变更 |
| **2–3 人** | 有第二个角色交叉评审 | `关键三关` | 开 | 开 | 仅关键变更 |
| **严格** | 对外交付 / 高风险 | `每阶段` | 开 | 开 | 每次都同步 |
| **全自动** | 小工具 / 原型 / 试验性代码 | `全自动` | 关 | 开 | 仅关键变更 |
| **极小改动** | 只改几行、无须中途把关 | `只在交付验收` | 关 | 开 | 仅关键变更 |

> **预设只是选档的快捷方式，最终落盘的必须是上表「审批模式」列的档位名**，
> 与 §0-B「审批模式五档」一字不差。别写「单人模式」「三关预设」这类描述进 `团队配置.md` ——
> 那不是档位名，agent 下次读会认不出来。

**全自动**：在 `团队配置.md` 写 `审批模式：全自动` 即启用。全程不呈现门禁、澄清问题自答、
按推荐项往下跑，只在四种情况下刹车（需求矛盾 / 不可逆对外动作 / 与需求冲突 / 必须加需求外功能）。
收尾**必须**输出 `开发文档/<类型目录>/CR-0X-<简称>/验收报告.md`，把「我替你决定的」逐条列出来。
**不要擅自开这一档**——用户明确写进团队配置才用；生产变更、对外交付不要用。

**`仅需求审批`**：写 `审批模式：仅需求审批` 启用。需求阶段可问一轮（≤5 题），产出 `需求.md` 后 **G1 停下等你批准**；
批准后 G2/G3 不生效，按全自动规则连续跑完，同样交 `验收报告.md`。G1 未批不许进设计。

**其余三档**（`关键三关` / `每阶段` / `只在交付验收`）的细则见 `references/extensions/team/role-gates/role-gates.md`，
此处不重复 —— **同一件事只许有一处权威**，两处各写一份，改一处漏一处就是下一条「注释和档位打架」。
档位名一律以 §0-B 的五档表为准。

**单人场景不要开 `approve-continue`**：它把「批准」和「继续」拆成两步，本意是让批的人和执行的人分开；
一个人兼两个角色时，这一步只会变成自己批给自己、再等自己说继续，纯增摩擦。
单人用门禁默认的 C 选项（批准并继续），一步到位。

## 7. 绝对不要做的四件事

1. 不要在没读完对应规则文件的情况下执行某个阶段；
2. 不要在用户没有明确批准时进入下一阶段（「看起来没问题」不算批准，要用户明说）；
3. 不要覆盖审计文件，也不要概括用户的原始输入；
4. 不要把应用代码写进 `开发文档/`。
