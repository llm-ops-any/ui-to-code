# 问题：上传图片后生成的 HTML 与图片内容无关

- 编号：CR-16102700
- 类型：缺陷
- 提出人：张勇（人编号 1）
- 提出时间：2026-10-27
- 状态：诊断完成 · 等方案选择
- 诊断时间：2026-10-27T11:00

## 1. 现象（用户原话）

> 我上传的图片，生成的 html 内容完全不是图片内容。……这是大模型问题吗，但是我从 llm-ops 平台测试生成的 html 一点问题没有

本地链路：前端上传图 → COS → `POST /api/chat`（body 带 `image_urls`）→ 转发 `LLMOPS_API_BASE/chat` → 模型返回的 HTML 与截图无关。

## 2. 实测证据（本地 dev server + 真实 COS 图，2026-10-27）

被测图片：`uploads/1793069632412.jpg`（548001 字节，实为 PNG 内容，与用户平台侧 curl 里 `files[0].size` 一致）。
人工核对：该图是**百度首页**（顶部 Bai 百度 logo、"百度一下"蓝色按钮、百度热搜列表）。

对照实验全部打到 `http://localhost:3000/api/chat`（服务端自动补 `app_id` + `Bearer`）：

| 实验 | 请求字段 | 图片 URL | 模型回答 | 判定 |
|---|---|---|---|---|
| A | `image_urls` | 项目上传的 jpg | 「I can't see any screenshot… no image came through」 | 没收到图 |
| B | `files[]`（完整 8 字段） | 项目上传的 jpg | 「Apple 网站首页」 | 编造 |
| C | `files[]` 仅 kind+url | — | `validate_error`：附件名称不能为空 | 缺 `name` 报错 |
| D | `files[]` 仅 kind+name+url | 项目上传的 jpg | 「Vercel 风格落地页」 | 编造 |
| E | `files[]` 完整 | 平台原生上传的 png（Content-Type 真实） | 「Tailwind CSS 官网」 | 编造 |
| F | `image_urls` | 平台原生上传的 png | 「no screenshot was included」 | 没收到图 |
| G | `files[]` + 「逐字抄出蓝色按钮文字」 | 平台原生上传的 png | 「Search」（正确应为「百度一下」） | 看不到图 |
| H | `files[]` + 「原样回显你收到的用户消息」 | 平台原生上传的 png | 见下 | **铁证** |

实验 H 模型回显的实际 prompt：

```text
<用户 query>

-----
用户随本条消息上传了1个附件，以下为附件信息(文本内容或文件地址)，请结合附件信息回答用户提问：

【附件1】1-3 百度首页.png（图片）
文件地址：https://....cos.ap-beijing.myqcloud.com/2026/10/27/ac10db96-....png
-----
```

**模型拿到的只有一行 URL 文本，没有任何图片像素。** `image_urls` 连这行文本都不会生成。

## 3. 根因（读 LLMOps 平台源码确认）

本项目 `/api/chat` 是纯转发，无字段转换。平台侧：

1. **`image_urls` 根本不是接口字段。** 在 `LLM-Ops-python` 全库 `.py` 中 **0 次出现**；开放 API 只认 `files: ListField`（`api/internal/schema/openapi_schema.py:34`）。⇒ 项目现在传的字段被**静默丢弃**。
2. **`files` 里的图片也不会变成视觉输入。** 平台唯一的消费点是
   `api/internal/lib/helper.py:58-120  build_query_with_attachments()`：有 `text` 就拼文本，只有 `url` 就拼一行「文件地址：<url>」——**纯字符串**。
3. **全库没有任何多模态消息构造**：无 `HumanMessage(content=[{"type":"image_url",…}])`；`ModelFeature.IMAGE_INPUT` 除定义外**零引用**（`api/internal/core/language_model/entities/model_entity.py:62-66`）。
4. 图片附件的 `text` 恒为空：`AttachmentTextExtractor.is_parseable()` 对 png/jpg 返回 False，全库无 OCR；`upload_file_handler.py:110` 那句 note「可使用其文件地址进行视觉理解」**只是给人看的说明**，`build_query_with_attachments` 从不读 `note`。
5. 平台自己的调试对话 / WebApp / 辅助 Agent 与开放 API **走同一个函数**，所以「平台里测没问题」不等于平台真把图喂给了模型。

⇒ **不是大模型问题，也不是本项目单方传参问题：平台后端的图片输入能力是「预留未实现」。**

## 4. 「平台测试没问题」的解释

平台侧那条 curl 同样只有 URL 文本。模型会顺着文件名 / query 编一份「看起来成立」的 HTML；用户只看到"有输出、像个页面"，很难分辨它是不是照着那张图做的。
建议复测方式：在平台里问一个**必须看图才能答对**的问题（例：图中的蓝色按钮上写了哪四个字），若答错即与本地同因。

## 5. 影响

- 主功能（截图 → 代码）实质不可用，输出与图片无关。
- 附带问题：`src/app/api/upload/image/route.ts:15,23` 把任意图存成 `uploads/<时间戳>.jpg` 且声明 `Content-Type: image/jpeg`（实测 PNG 内容被声明成 jpeg）。本问题中不影响平台拉取，但是独立隐患。

## 6. 修复方案（待选）

| 方案 | 做什么 | 前置 | 代价 |
|---|---|---|---|
| **A 平台补多模态（正解）** | 在 LLM-Ops-python 里把 `kind=image` 附件构造成多模态 content，并用 `IMAGE_INPUT` 做能力开关；同时兼容 agent 对 list content 的处理（敏感词检测 / HumanMessage 重建 / token 统计） | 视觉模型已有：`qwen3-vl-plus`、`deepseek-v4-flash-vision-exp`（均带 `image_input`） | 跨项目 CR；改完需 `docker compose build llmops-api` + `restart llmops-nginx` |
| **B 本项目自己看图** | 服务端先把截图送视觉模型转成结构化描述，把描述当 `files[].text` 传给平台（走平台现成的文本通道，无需改平台） | **需要一个可直连的视觉模型凭证**（当前 `.env` 只有 `LLMOPS_*` 与 `COS_*`） | 多一跳、多一份成本；描述质量决定还原度 |

**两个方案都必须做的事（本项目侧）**：把 `image_urls: string[]` 换成平台唯一的 `files: object[]`（每项至少 `name` + `url`，建议补 `kind/mime/extension/size`）。只改这一项**不足以修复**本问题（实验 B/E 已证）。

## 7. 结论

- 现状：**已修复**（2026-10-27）。
- 选型：PO 选方案 A。上游 `LLM-Ops-python` `CR-16102701` 实现多模态图片输入（视觉模型下 `files[].url` 作为图片传入），
  并把该应用模型由 `deepseek-flash` 切为 `qwen3-vl-plus`（回滚 SQL 见上游 `变更说明.md` 差异 1）。
- 本项目落地：`src/models/chat.ts`、`src/app/page.tsx`、`src/app/api/upload/image/route.ts`
  （`src/app/api/chat/route.ts` 纯透传，未改）。
- 验收证据：见 `验收报告.md` §3 —— 问截图中按钮文字，模型答出 `百度一下`。
